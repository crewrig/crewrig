# Modernize the gitlab-ci skill to the authoring standard

*Delta 01 of `specs/0301-gitlab-ci-modernization.md`. Source: issue #1940, the capture step required by R6 and R10 ("the markers above SHALL be checked against a real capture before the script is written; a capture that disagrees with them is raised as a spec finding"). Real captures of `glab ci lint` (glab 1.130.0) disagree with the recognised markers of R6: a valid pipeline prints `Validating...` then `✓ CI/CD YAML is valid!` and exits 0, but an invalid pipeline prints `Validating...`, then `<file> is invalid.`, then one numbered error line, and exits 1 with an empty standard error. The string `CI/CD YAML is invalid` never appears, so the original invalid marker would classify every invalid pipeline as unrecognized output. GitLab returns only the first error of a file. An authentication failure, a connection failure and a run outside a repository all exit 1 with a standard error that starts with `you must be in a GitLab project repository for this action:` and then names the cause (`401 Unauthorized`, `no such host`, `not a git repository`). Requirements modified: R6 (markers, mapping, error lines, honesty about what glab reports), R10 (the stub tests and the captured fixtures) and the scenarios that depend on them. Every other requirement is unchanged. This delta opens no question.*

## ADDED

### Failure path — authorization or network failure is not a verdict

- **Given** a `GLAB_BIN` stub that replays the captured authorization failure (exit 1, empty standard output, standard error `you must be in a GitLab project repository for this action: ... 401 {message: 401 Unauthorized}.`) or the captured network failure (same prefix, then `no such host`), each with the project path, host and user names scrubbed,
- **When** `lint-gitlab-ci.ts` runs,
- **Then** it exits 3 with a `precondition` finding whose message names an authentication failure or a connection failure respectively and says the pipeline was NOT validated server-side, `ok` is false, and no `invalid-config` finding is reported.

### Failure path — outside a repository

- **Given** a stub that replays the captured run outside a git checkout without `--repo` (exit 1, standard error starting with `you must be in a GitLab project repository for this action:` and ending with `not a git repository`),
- **When** `lint-gitlab-ci.ts` runs,
- **Then** it exits 3 with a `precondition` finding saying the pipeline was NOT validated server-side, and it never reports the pipeline as valid or invalid.

## MODIFIED

6. **R6 (lint-gitlab-ci script), recognition and mapping, original:** "... it SHALL run `glab ci lint` on that file and recognise the outcome from the exit code of glab together with its printed text, because glab uses no distinct exit code for an invalid configuration as against an authentication or connection failure. The recognised markers are the substrings `CI/CD YAML is valid` and `CI/CD YAML is invalid`, matched case-insensitively and ignoring any leading symbol or whitespace. The mapping is: (a) valid: the valid marker is present, the invalid marker is absent and glab exited 0; ... (b) invalid: the invalid marker is present, whatever the exit code and even when the valid marker also appears, so invalid takes precedence; the script exits 1 with one finding of rule `invalid-config` per non-empty line glab prints after the invalid-marker line, each stating that line; when none follows, a single finding carries the marker line; (c) not validated: glab is not installed, glab was killed after the bounded wait ..., or the output holds neither marker, including an exit 0 with no marker; ... naming the cause (missing binary, timeout, authentication failure, connection failure or unrecognized output) ... Naming an authentication or a connection failure is best effort on glab's text; ... The markers above SHALL be checked against a real capture before the script is written (R10); a capture that disagrees with them is raised as a spec finding rather than patched around."

**Amended (R6, recognition and mapping only):** The script SHALL recognise the outcome from the exit code of glab together with its standard output and standard error, because glab uses the same exit code, 1, for an invalid configuration, an authentication failure, a connection failure and a run outside a repository. The two markers, checked against real captures of glab 1.130.0, are:

- the **valid marker**: the substring `CI/CD YAML is valid`, matched case-insensitively and ignoring any leading symbol (glab prints a check mark) or whitespace and any trailing punctuation;
- the **invalid marker**: a line that, once trimmed, ends with the words `is invalid.` and that follows the `Validating...` line, matched case-insensitively. The line starts with the name of the linted file. The string `CI/CD YAML is invalid` is NOT a marker, because glab never prints it.

The mapping is: (a) valid: the valid marker is present, the invalid marker is absent and glab exited 0; the script exits 0 with `data` naming the file and the verdict; (b) invalid: the invalid marker is present, whatever the exit code and even when the valid marker also appears, so invalid takes precedence; the script exits 1 with one finding of rule `invalid-config` per non-empty line glab prints after the invalid-marker line, each stating that line, which is the numbered error message; when no line follows, a single finding carries the marker line. GitLab reports only the first error of a file, so one finding per run is the normal case and several are possible only if glab prints several lines; (c) not validated, which covers everything else: glab is not installed, glab was killed after the bounded wait (30 seconds by default, `--timeout <seconds>` to change it), glab exited non-zero with neither marker (an authorization failure, a network failure, a run outside a git repository, any other failure), or the output holds neither marker, including an exit 0 with no marker; the script exits 3 with a finding of rule `precondition` whose message names the cause (missing binary, timeout, authentication failure, connection failure, not a repository or unrecognized output) and says the pipeline was NOT validated server-side. Naming the cause is best effort on the text of standard error: `401 Unauthorized` is an authentication failure, `no such host` a connection failure, `not a git repository` a run outside a repository; any text the script cannot classify is reported as unrecognized output. A wrapped line of standard error SHALL NOT defeat the classification, so the script matches on the whitespace-normalised text. Unclassifiable output is never reported as valid. The rest of R6 is unchanged, including the order of checks, the kill on timeout, `GLAB_BIN`, and the rule that the script writes nothing, passes nothing to glab but the file and `--repo`, and reads no credential. The checking of the markers against a real capture is done by this delta; R10 keeps the capture as a committed fixture.

10. **R10 (script tests), `lint-gitlab-ci.ts` part, original:** "The tests of `lint-gitlab-ci.ts` SHALL drive it only through a `GLAB_BIN` stub and SHALL cover: a valid verdict, an invalid verdict with two errors, output carrying both markers (invalid wins), exit 0 without a marker, a missing binary, an authentication failure, a connection failure, a hang past the timeout in which the stub's process is proved gone afterwards, and unrecognized output. Before the script is written, the contributor SHALL capture the real output of `glab ci lint` for one valid and one invalid pipeline, record the glab version, and commit both captures as fixtures that the stub replays; the other stub outputs are derived from them."

**Amended (R10, `lint-gitlab-ci.ts` part only):** The tests of `lint-gitlab-ci.ts` SHALL drive it only through a `GLAB_BIN` stub and SHALL cover: a valid verdict, an invalid verdict (the single error of the real capture, and a derived output with two numbered lines to prove one finding per line), output carrying both markers (invalid wins), exit 0 without a marker, exit 1 without a marker, a missing binary, an authorization failure, a connection failure, a run outside a repository, a hang past the timeout in which the stub's process is proved gone afterwards, and unrecognized output. The stub SHALL replay real captures, not text written from memory: the contributor SHALL commit as fixtures the captured output (standard output, standard error and exit code, one file set per case) of `glab ci lint` for a valid pipeline, an invalid pipeline, a rejected token, an unreachable host and a run outside a git checkout, together with the glab version (1.130.0 for the captures this delta rests on). The authorization failure and the network failure SHALL each have their own fixture, distinct from the valid and invalid ones, because their text and their exit code differ from a verdict. Before a capture is committed, project paths, group and project names, host names and user names SHALL be scrubbed from it, replaced by neutral placeholders (for instance `group/project` and `unreachable.invalid`) in a way that keeps the shape of the text (prefix, status, cause) intact. The other stub outputs (both markers, exit 0 or exit 1 without a marker, unrecognized text, two numbered lines) are derived from those captures. The rest of R10 is unchanged.

The scenarios of the original spec that depend on the markers read as follows from now on; those not listed are unchanged.

- **"Happy path — valid pipeline", amended:** the stub replays the captured valid output (`Validating...`, then `CI/CD YAML is valid!`, exit 0); the script exits 0 and, under `--json`, prints `ok: true` with no finding.
- **"Failure path — invalid pipeline", amended:** *Given* a stub that replays the captured invalid output (`Validating...`, a line `<file> is invalid.`, one numbered error line, exit 1, empty standard error), *When* `lint-gitlab-ci.ts` runs, *Then* it exits 1 with one `invalid-config` finding carrying the error text; and *Given* a derived output with two numbered error lines after the invalid line, it exits 1 with two `invalid-config` findings, each carrying one line.
- **"Failure path — both markers", amended:** the stub output carries a line `<file> is invalid.` and the text `CI/CD YAML is valid`, and exits 0; invalid takes precedence, so the script exits 1 with an `invalid-config` finding.
- **"Failure path — offline degrades without a false pass", amended:** the stub (or an absent binary) replays the authorization failure or the network failure, runs outside a repository, hangs past the timeout or prints an unrecognized answer, or exits 1 with no marker; the script exits 3 with a `precondition` finding naming the cause and stating the pipeline was NOT validated server-side, and `ok` is false. The authorization and network cases are pinned by their own fixtures (scenario added above).

## REMOVED

Nothing is removed. The invalid marker `CI/CD YAML is invalid` of R6 is replaced, not deleted: it is superseded by the line ending with `is invalid.` defined above.
