# Uniform, verified Task provisioning

## Intent

Every CI job that runs `task` first installs it, and today that install is fail-open: `sh -c "$(curl ... taskfile.dev/install.sh)"` exits 0 when `curl` fails, because the shell then runs an empty string. A job can therefore proceed with no `task`, or an unpinned, unverified one (issue #1770 finding v1-F1, ledger #961). This is slice 2 of `specs/0280-task-ci-contract.md` (R3, with the invariants of its R9 and the measurement of its R10), whose slice 3 migrates every job to `task ci:<id>` and so depends on a verified `task` (0280 R7). Its predecessor is slice 1, `specs/0281-split-checker-selftests.md` (merged). The slice replaces the six copies of the install on each engine with one mechanism per engine, pinned, checksum-verified, fail-closed, and adds a guard that keeps it that way.

## Requirements

1. **R1 (inventory, measured on origin/main 7a1707f3).** The slice SHALL replace every route that provisions Task in CI. The measured routes are: on GitHub, six `Install Task` steps, five in `.github/workflows/build.yml` (jobs `check-taskfile-tree`, `check-taskfile-tree-selftest`, `ci-pre-push-replay`, `cli-matrix-fresh`, `lint-specs`; lines 2029, 2077, 2118, 3694, 3751) and one in `.github/workflows/changeset-coverage.yml` (line 32, the only one that already ends with `task --version`); on GitLab, six `sh -c "$(curl --location https://taskfile.dev/install.sh)" -- -d -b /usr/local/bin` lines in `.gitlab-ci.yml` (lines 1733, 2593, 2619, 2678, 2755, 3291, one per job above) generated from the single recipe `task` at line 40 of `scripts/lib/build-ci/tools.ts`, selected by `requires.tools: [task]` in `ci/ci-capabilities.yml` (six capabilities: the five ids above plus `changeset-coverage`). No other workflow under `.github/workflows/` and none of the 24 `windows-latest` jobs runs `task`; no macOS job exists. The remaining mentions are human instructions and stay: the README prerequisites row for Task (line 237), `tests/e2e/README.md` line 13, `docs/runbooks/custom-ca-tls-trust.md` line 151, and the `.githooks/pre-push` error message. Acceptance: after the slice, `grep` for `taskfile.dev/install.sh` over `.github/`, `.gitlab-ci.yml`, `scripts/lib/build-ci/` and `ci/` finds nothing, and the assertions that today require that string in `scripts/tests/check-taskfile-tree-ci-wiring.test.ts` (lines 164 and 180) assert the new mechanism instead.

2. **R2 (one pin, one place).** The Task version and its checksums SHALL live in exactly one committed file, `ci/task-pin.json` (`{ "version": "<x.y.z>", "sha256": { "<platform>": "<hex>" } }`), parsed with `JSON.parse` only. The version SHALL be at or above the floor of spec 0278 R8, which is the `version:` string of the root `Taskfile.yml` (today `'3.39'`); the guard of R6 reads that string and fails when the pin is below it. Both engine mechanisms SHALL read this file: the composite action of R4 at run time, and `scripts/lib/build-ci/tools.ts` at generation time, so a pin change is one edit to `ci/task-pin.json` plus a regeneration of `.gitlab-ci.yml`. Update procedure, documented in `docs/ci-reference-format.md`: pick a release, copy the `task_<platform>` lines from the release's published `task_checksums.txt` into the file, run `task build-ci` (or the repository's regeneration entry), and let CI prove it; no step needs a token. The permitted carriers of the pin and of the checksums are exactly three: `ci/task-pin.json` (the source), the generated `.gitlab-ci.yml` (which necessarily embeds the pinned URL and the `sha256sum -c` line, R5), and `.github/actions/setup-task/action.yml`, which carries neither and only reads the pin by reference. Acceptance: outside those carriers, the guard of R6(d) finds no Task checksum and no pinned download URL, and a version bump is a two-file diff (`ci/task-pin.json`, `.gitlab-ci.yml`).

3. **R3 (verification and fail-closed, decision).** The mechanism SHALL download the release archive at the pinned URL `https://github.com/go-task/task/releases/download/v<version>/task_<platform>.<ext>` and verify its SHA-256 against the value in `ci/task-pin.json` before extracting. Decision: a pinned checksum, not a fetch of the release's `task_checksums.txt`, because a checksum fetched from the same origin as the archive proves nothing against a compromised release, whereas a pin reviewed in a PR does; this is the repository's own precedent for `yq` and `jq` in `scripts/lib/build-ci/tools.ts` (pinned URL, `sha256sum -c`). Signature verification (the release's cosign signature of the checksums file) is rejected for now: it adds a tool to provision on every runner for the same assurance the pin gives, and it MAY be revisited in a later spec. Every failure SHALL exit non-zero: a failed download (`curl --fail --silent --show-error --location` with `--retry 3`, never `sh -c "$(curl ...)"`), a checksum mismatch, an unsupported platform, and a `task --version` that does not print the pinned version. The step SHALL end with `task --version` compared to the pin. The verification SHALL be bash-only (`curl`, `sha256sum` or `shasum -a 256`, `tar`, and a string comparison), with no dependency on Node or any tool provisioned by an earlier step, so it is correct at any step position in a job, including before `actions/setup-node`. Rate limits and outages: the download is a plain release-asset URL, not an API call, so it has no token and no API rate limit; after the retries it fails the job, and a re-run is the remedy; there is no fallback to an unverified source and no cached unverified binary. Local development is unaffected (the README route for humans stays). Acceptance: fixtures (R6) show non-zero exit for a failed download, a wrong checksum and a version mismatch, and zero for a good pin.

4. **R4 (GitHub: local composite action).** A composite action `.github/actions/setup-task/action.yml` SHALL implement R3 and every GitHub job that runs `task` SHALL use it as `uses: ./.github/actions/setup-task` in place of its `Install Task` step, keeping its existing `if: steps.filter.outputs.<id> == 'true'` condition, and the `sudo` install into `/usr/local/bin` SHALL be preserved. The action holds the verification logic once, as bash only, inline in the `run:` of its step: it reads `ci/task-pin.json` with shell tools, so it needs no Node and no ordering beyond running after the checkout (the pin file must exist). The logic is inline, not a new `scripts/*.sh` file, because the footprint ratchet of spec 0238 (`scripts/check-ratchet.ts`) fails when an entry is added to `ci/shell-allowlist.txt`, so a new tracked shell file is not allowed. The action SHALL read the pin path and the archive URL from environment variables that default to the repository pin and the release URL, so the tests of R7 can point them at a local pin and a `file://` archive. Platforms: Linux (`ubuntu-latest`, `linux_amd64`) is implemented and tested now. Windows decision: the action SHALL run its steps with `shell: bash` (Git for Windows, present on `windows-latest`) so that the commands stay within the Windows-command rule of spec 0266 (`scripts/check-taskfile-commands.ts`: no `jq` and no Unix utility absent from Git Bash), and on a non-Linux runner SHALL fail closed with a message naming the platform until the `windows_amd64` checksum is added to the pin and the archive extraction (`task_windows_amd64.zip`, extracted by the system `tar` that handles zip) is proven on a Windows runner; that proof belongs to the first Windows job that needs `task`, in slice 3 (#1780), because no Windows job runs `task` today. Acceptance: zero `Install Task` steps remain in `.github/workflows/`; the six jobs of R1 use the action; running the action on a platform without a pinned checksum exits non-zero.

5. **R5 (GitLab: recipe in `tools.ts`).** The `task` entry of `TOOLS` in `scripts/lib/build-ci/tools.ts` SHALL become a multi-line recipe of the same shape as `yq`: install `curl` and `ca-certificates` when absent, download the pinned archive with `curl --fail`, `sha256sum -c` against the pinned value, extract to `/usr/local/bin`, and end with a `task --version` check, none fail-open. Plumbing: `ci/task-pin.json` is read once, at generation, by the `build-ci` entry, which resolves the repository root as it already does for the capability reference and passes the parsed pin to the recipe builder; `toolInstallLines` stays a pure function of its arguments (the pin is a parameter, so tests call it without a checkout and `build-ci --check` is deterministic). A missing or malformed pin, or a platform without a checksum, SHALL fail generation closed with a `BuildCiError` naming the file. The six generated jobs in `.gitlab-ci.yml` SHALL be regenerated. Acceptance: `node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON scripts/build-ci.ts --check` and `scripts/check-ci-parity.ts` exit 0, and `.gitlab-ci.yml` holds no `taskfile.dev` string.

6. **R6 (guard).** A guard script `scripts/check-task-provisioning.ts` SHALL exit non-zero and name the job (and the file) when: (a) a GitHub job that needs Task has no `uses: ./.github/actions/setup-task` step, or has that step before its `actions/checkout` step (any position after the checkout is accepted, because the jobs also run `dorny/paths-filter`, `actions/setup-node` and `npm ci` first), or contains a step that installs Task by another route; a job needs Task when its capability has `requires.tools` containing `task` in `ci/ci-capabilities.yml`, the GitHub job being mapped to its capability by id through the parity job records (not by scanning step commands, because no GitHub step invokes `task` before slice 3, and any `task` invocation found in a `run:` step additionally marks its job as needing Task); the install-by-another-route test covers (`taskfile.dev`, `go-task`, `install.sh`, a `sh -c "$(curl` command substitution, `brew`, `choco`, `scoop`, or `npm` install of Task) in any step; (b) a GitLab job whose capability requires `task` does not carry exactly the generated recipe of R5, or any job carries a fail-open command of the same substitution form; (c) the composite action lacks the fail-closed elements of R3 (checksum verification, the `task --version` check, no `|| true` and no `continue-on-error`); (d) `ci/task-pin.json` is malformed or below the floor of R2, or a duplicate of the pin exists. Duplicate-search scope: the files of `.github/` (workflows and actions), `.gitlab-ci.yml`, `ci/`, `scripts/` excluding `scripts/tests/`, and `taskfiles/`; documentation, `specs/` and test fixtures are not searched, so prose naming a version does not trip the guard. The searched patterns are the 64-hex checksums of the pin and the download URL with the literal pinned version substituted (the URL templates built from the pin in `scripts/lib/build-ci/tools.ts` and in the action are not matches, and those files are in scope only for the literal forms); the allowed carriers are `ci/task-pin.json`, the generated `.gitlab-ci.yml` (which MUST match the `build-ci` output for the current pin, so a stale copy is also a failure), and the composite action by reference only (it MUST NOT contain either pattern). It SHALL reuse `scripts/lib/ci-parity/reference-read.ts` and the existing job-record extraction of `scripts/lib/ci-parity/` (`job-records.ts`, `gha-arm.ts`, `gitlab-arm.ts`), `scripts/lib/taskfile-tree.ts` for the floor, and `scripts/lib/glob-engine.ts` for path matching, and SHALL add no YAML parser and no framework. Acceptance: it exits 0 on the repository and non-zero, naming the job, on each of these `mkdtemp` fixtures: a job with the former `Install Task` step; a job with a checksum-less download; a job that needs Task with no provisioning; a job whose setup-task step comes before its checkout; a GitLab job with the old recipe; an action with `|| true`; a pin below the floor; a checksum or pinned URL duplicated in a workflow or in the action, and a stale `.gitlab-ci.yml` carrier; the generated `.gitlab-ci.yml` carrier alone is accepted.

7. **R7 (tests, wiring, tiers).** The guard SHALL have fixture tests `scripts/tests/check-task-provisioning.test.ts` (R6 cases, plus the R3 failure cases run against the `run:` script extracted from the action (with the YAML reader the repository's scripts already use, no new parser) and executed under bash with a local pin and a `file://` archive in place of the network) using only `mkdtemp` directories, and a wiring test in the style of `scripts/tests/check-taskfile-tree-ci-wiring.test.ts`. Following spec 0281, the CI wiring SHALL be two capabilities in `ci/ci-capabilities.yml`: `check-task-provisioning` (runs the guard) and `check-task-provisioning-selftest` (runs the tests), each with its own `paths:` (the action, `ci/task-pin.json`, `.github/workflows/**`, `.gitlab-ci.yml`, `ci/**`, `scripts/lib/build-ci/**`, `scripts/lib/ci-parity/**`, the guard and its tests), a `build.yml` job each, regenerated `.gitlab-ci.yml` jobs, and the tests listed so `scripts/check-test-wiring.ts` stays green. Whether the guard also joins the fast tier of `ci/pre-push-tier.json` (spec 0279 R9) is the PLAN's call, decided by its measured time against the admission cap, and any join keeps `ci:pre-push` within its budget. The slice SHALL NOT modify `.githooks/pre-push` or `scripts/ci-pre-push.ts`, SHALL NOT migrate any job to `task ci:<id>` (slice 3, #1780), and SHALL add no task to the root `Taskfile.yml`. Acceptance: the new tests pass under `node --test`, `check-test-wiring` and `check-ci-parity` are green, and the diff touches neither pre-push file.

8. **R8 (invariants and measurement).** At its merge the slice SHALL satisfy the invariants of 0280 R9: CI green; reversible by reverting its PRs (the pin file, the action, the regenerated `.gitlab-ci.yml`, the guard and its wiring revert together); `.gitlab-ci.yml` regenerated and `check-ci-parity` green; `cancel-on-failure`, `changeset-coverage` and `path-ownership` working (the `changeset-coverage` job keeps its other tool installs and only swaps its Task step); every task name stable; and no new framework or YAML parser. The PR SHALL report the line counts of the R10 surfaces against the baseline 12,681 and against the state after slice 1 (13,956: `.github/workflows/build.yml` 4,122; `ci/ci-capabilities.yml` 5,675; `.gitlab-ci.yml` 4,159), per surface and in total. Expectation, not a threshold: `build.yml` shrinks (each install step collapses to a `uses:` line but keeps its `if:` line) and `.gitlab-ci.yml` and `ci/ci-capabilities.yml` are expected to grow (a multi-line recipe repeated in six jobs, two new capabilities); the PR states the measured deltas and promises no figure, and the 30% target is met by slices 3 and 5. The R10 measure owned here is: zero `Install Task` steps that are not verified. Acceptance: the report is in the PR; a grep-based check and the guard show zero unverified Task installs.

## Scenarios

**Scenario:** A failed download fails the job

Given a job that provisions Task through the composite action
When the release download fails or returns an archive whose SHA-256 differs from `ci/task-pin.json`
Then the step exits non-zero, no `task` binary is installed, and the job is red.

**Scenario:** A version mismatch fails the job

Given a downloaded and verified archive whose `task --version` differs from the pinned version
When the final check runs
Then the step exits non-zero.

**Scenario:** The old install is rejected by the guard

Given a workflow job with a step `sh -c "$(curl --location https://taskfile.dev/install.sh)"` that later runs `task`
When `scripts/check-task-provisioning.ts` runs
Then it exits non-zero and names that job and file.

**Scenario:** The repository is clean

Given the repository after the slice
When the guard runs
Then it exits 0, every job that runs `task` uses `./.github/actions/setup-task` or the generated GitLab recipe, and `.gitlab-ci.yml` equals the `build-ci` output.

**Scenario:** Bumping the pin is one edit

Given a maintainer wants Task 3.54.0
When they edit `ci/task-pin.json` with the published checksums and regenerate `.gitlab-ci.yml`
Then both engines install 3.54.0, and a pin below the floor `3.39` is refused by the guard.

**Scenario:** A non-Linux runner is refused, not guessed

Given a Windows job that uses the composite action before its checksum is pinned
When the action runs
Then it exits non-zero naming the platform instead of falling back to an unverified install.

## Out of scope

- Migrating any job to `task ci:<id>` (slice 3, #1780), including the first Windows job that runs `task` and the proof of the Windows archive extraction.
- `.githooks/pre-push`, `scripts/ci-pre-push.ts` and the pre-push tier mechanics (spec 0279), except a possible tier entry per R7.
- Provisioning of `yq`, `jq`, `tesseract`, Node or any tool other than Task; unifying them behind the same action is a later choice.
- Cosign or other signature verification of releases; a release mirror or a cache of the archive.
- Human installation instructions (README, runbooks), which keep their current form.

## Open questions

- Windows extraction: is the system `tar` on `windows-latest` enough to extract `task_windows_amd64.zip` under Git Bash, or does the first Windows job need another documented step? To settle in slice 3 with a measurement; this slice fails closed meanwhile (R4).
- Does the guard join the fast tier of `ci/pre-push-tier.json`? To settle in the PLAN from its measured time (R7).
- Which Task version is pinned first: the newest release at authoring time, or the lowest version proven by the repository's existing checks (0278 verified 3.39.0 and 3.54.0)? To settle in the PLAN; the guard accepts any version at or above the floor.
