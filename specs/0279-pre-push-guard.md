# Pre-push guard

## Intent

Avoidable red CI (Markdown lint, broken links, spec format, TypeScript format and typing, test wiring, CI parity, component drift) costs a round trip of minutes on every occurrence, and it hits every agent that pushes with `git`, whatever its CLI. After this spec, a native git `pre-push` hook runs, locally and within 60 seconds on a typical change, the fast subset of the CI checks that the pushed changeset can affect, using the same commands CI runs, so those failures are caught before the push. CI stays authoritative: the hook is a convenience that can be bypassed with `git push --no-verify`, never a gate. This is work package WP-B (#1763) of epic #1761. It depends on WP-A (spec 0168 delta-01, merged), because without it the hook would block every push of a spec branch on spec 0168 R1; it builds on WP-T (spec 0278), which created the empty `taskfiles/ci.yml` file this spec fills.

The issue text (#1763) names the entry point `task check:pre-push` and the installer `task hooks:install`. Both predate the Taskfile split of #1764 (spec 0278 R1), which forbids adding a task to the root `Taskfile.yml` and reserves `taskfiles/ci.yml`, namespace `ci`, for this work. The names are therefore `ci:pre-push` and `ci:hooks-install`.

## Requirements

1. **R1 (layout).** Every task this spec adds SHALL be defined in `taskfiles/ci.yml`, included under the namespace `ci` (already wired by spec 0278 R4). No task SHALL be added to the root `Taskfile.yml` or to another domain file, except the edit of R6 to the existing `lint-markdown` task. The entry point is `ci:pre-push`; the installer is `ci:hooks-install` (R14). Acceptance: `scripts/check-taskfile-tree.ts` passes, `task --list-all --json` shows the new `ci:*` names only, and the name-set baseline fixture of spec 0278 R6 is updated to the new set (the baseline is extended, never relaxed or bypassed).
2. **R2 (one task per reused CI job).** For every capability of `ci/ci-capabilities.yml` admitted to the fast tier (R9), `taskfiles/ci.yml` SHALL define a task `ci:<capability-id>` that runs exactly that capability's CI command, as R3 defines "exactly". The first such task is `ci:check-taskfile-tree`, the work deferred to this ticket by #1764. Where a domain task already runs a command of the capability (`spec:lint`, `lint-markdown`, `lint-ts`, `ratchet`, `host-safety`, `check-skill-versions`, `check-description-length`, `check-taskfile-commands`, ...), `ci:<id>` SHALL call it with `- task: :<name>` instead of repeating the command text. Every `- task:` call from `taskfiles/ci.yml` SHALL use the colon-anchored global form (`- task: :lint-markdown`, `- task: :spec:lint`), because `resolveTaskRef` resolves an unanchored name written in `ci.yml` to `ci:<name>`, which for `lint-markdown` is the task itself. Acceptance: the parity check of R4 passes for every `ci:<id>`, and `git grep` finds no command text duplicated between `taskfiles/ci.yml` and a domain file.
3. **R3 (what "exactly the CI command" means).** The command of a capability is the ordered `command:` list of its entry in `ci/ci-capabilities.yml`. After normalisation, the ordered command list that `ci:<id>` resolves to SHALL equal it. The normalisation is closed and has four steps, applied identically to both sides: (a) drop provisioning commands (R5); (b) expand every `task <name>` command of the capability, and every `- task:` call of the Taskfile side, into the command text of the called task (recursively; the loader of spec 0278 R10, `scripts/lib/taskfile-tree.ts`, returns command text unexpanded, so the guard performs this expansion itself, resolving each reference with the loader's `resolveTaskRef`); (c) strip the exact prefix `{{.REPO_DIR}}/` wherever it appears in a command, and drop a trailing `{{.CLI_ARGS}}` token, because domain tasks write repository paths as `{{.REPO_DIR}}/scripts/...` where the capability commands use the bare relative path; (d) collapse runs of whitespace. Nothing else is normalised: flags, `--ignore` values, file lists, glob arguments and the `ci-cache-guard.ts --stray-scan --` wrapper are compared verbatim. The compared object is the resolved, normalised command list, not the textual body of the task: a `ci:<id>` task MAY mix `- task: :<name>` calls and raw commands, in the capability's order, so long as the resolved list equals the capability's. Worked example, `ci:check-taskfile-commands`: the capability lists `npm ci --omit=dev --workspaces=false` (provisioning, dropped by (a)), then `node ... scripts/check-taskfile-commands.ts`, then the stray-scan-wrapped `--test` run of its two test files; the domain task `check-taskfile-commands` holds only the second, so `ci:check-taskfile-commands` is `- task: :check-taskfile-commands` followed by the raw stray-scan-wrapped test command, and its resolved list equals the capability's once `npm ci` is dropped. A `ci:<id>` task MAY add `preconditions:` and `env:`; it SHALL NOT add a command the capability lacks, drop one it has, or reorder them. Acceptance: R4.
4. **R4 (parity by construction, mechanical).** A guard (suggested path `scripts/check-ci-pre-push-parity.ts`; the PLAN names it) SHALL fail, naming the capability id, the first differing command and both texts, when for any `ci:<id>` task other than the four control tasks (`ci:pre-push`, `ci:hooks-install`, `ci:hooks-uninstall`, `ci:hooks-status`, a closed set committed as a constant in the guard, so a fifth unlisted `ci:*` task without a capability still fails) (a) no capability `<id>` exists, (b) the normalised command lists of R3 differ, or (c) a capability in the tier list of R9 has no `ci:<id>` task. It SHALL read the capability file through `scripts/lib/ci-parity/reference-read.ts` (`readCapabilities`, `CapRecord`) and the Taskfiles through `scripts/lib/taskfile-tree.ts`; it SHALL NOT add a YAML parser. It SHALL print an explicit notice, never skip silently, when it cannot read either side, and exit non-zero. Acceptance: tests on `mkdtemp` fixtures prove that a changed flag, a dropped `--ignore`, a reordered command and a missing task each fail; that a difference consisting only of the `{{.REPO_DIR}}/` prefix (or a trailing `{{.CLI_ARGS}}`) passes while any other difference still fails; that an unanchored `- task: <name>` call (the negative case; every call in the spec text and in `ci.yml` is written `- task: :<name>`) in `ci.yml` to a name that also exists as `ci:<name>` fails the guard, and the anchored form passes; and that the real tree passes; the guard is wired per R16.
5. **R5 (provisioning rule).** Engine-level setup commands are provisioning, not checks: a command is provisioning if and only if it matches `^npm (ci|install)( |$)` (this covers `npm ci`, `npm ci --omit=dev --workspaces=false`, `npm install`, `npm install -g markdownlint-cli`). Provisioning commands SHALL be absent from `ci:<id>` and replaced by a precondition on the task: `check-tool-binaries.ts <binaries>` or `npx --no-install <tool> --version`, with the message `Run: task lint-bootstrap`, the pattern of `taskfiles/lint.yml`. The rule is a single exported constant used by the guard of R4, so the definition cannot drift between the guard and the tasks. A hook run SHALL never run `npm ci` or `npm install` itself (R13). Acceptance: tests show an `npm ci` line left in a `ci:<id>` task fails the guard, and an `npm ci` line in a capability does not appear in the resolved list.
6. **R6 (known drift: `lint-markdown`).** Two copies of the Markdown lint command exist today: the CI capability passes `--ignore communication` and does not pass `--ignore '**/node_modules/**'`, and the `lint-markdown` task does the opposite. Both SHALL converge on the union, `markdownlint "**/*.md" --ignore node_modules --ignore '**/node_modules/**' --ignore extension-skeleton --ignore communication --ignore 'extensions/**/commands/*.md' --ignore 'artifacts/*/commands/*.md'`, in `ci/ci-capabilities.yml` (with `.gitlab-ci.yml` regenerated, R16) and in `taskfiles/lint.yml`. Rationale: CI is the authority, so the task adds `--ignore communication` (the directory holds only `.gitkeep`, and its exclusion is the declared intent of CI); the capability adds the `node_modules` glob because a local checkout always has `node_modules` trees, and CI's checkout has them in some jobs, so the extra ignore is harmless there and necessary here. After this requirement `ci:lint-markdown` is `- task: :lint-markdown` and R4 proves the equality. Acceptance: R4 passes on `lint-markdown`; `task lint-markdown` and the CI job ignore the same set.
7. **R7 (known drift: `lint-specs`).** The capability `lint-specs` runs `node --test scripts/tests/spec-linter-*.test.ts` (wrapped in the stray-scan guard) and then `task spec:lint`. The capability is the authority: `ci:lint-specs` SHALL run both, in that order, the second as `- task: :spec:lint`. No change is made to the capability. `spec:lint` itself is unchanged. The spec-linter test files SHALL NOT depend on the ambient value of `CREWRIG_PR_DRAFT` (they SHALL clear it in the environment of the linter processes they spawn), because R12 sets it for the whole `ci:lint-specs` task. Acceptance: the spec-linter suite passes with `CREWRIG_PR_DRAFT=true` and with it unset.
8. **R8 (changeset-aware selection).** `ci:pre-push` SHALL run, as its first command, `node scripts/lib/node-floor-guard.js` (the pattern of `taskfiles/cli-matrix.yml`), so an old Node speaks through the guard before the wrapper has to parse TypeScript, and then `scripts/ci-pre-push.ts` (name suggested), which selects the checks to run as follows. (a) Base: the merge-base of `HEAD` and the target ref; the target ref is `origin/main` unless `CREWRIG_PRE_PUSH_BASE` names another ref. (b) Changeset: `git diff --name-only <merge-base>..HEAD`, committed changes only, because a push sends commits; uncommitted and untracked files never select or deselect a check. (c) Selection: a fast-tier capability runs when it has no `paths:` filter on its `pull-request` trigger (it always runs), or when at least one changed path matches one of those globs; matching uses `scripts/lib/glob-engine.ts`, which fails closed on a glob it does not support, and the capability records and globs are read through `scripts/lib/ci-parity/reference-read.ts` (`CapRecord`, `TriggerRecord`) and the gated-plan reader `scripts/lib/ci-changeset-coverage/reference.ts` (`gatedPlan`) wherever it already exposes them. There is no second source of truth for paths, no second glob matcher and no second YAML parser. (d) A capability without a `ci:` task never runs in the hook. (e) The wrapper SHALL set `BASE_REF` to the target ref name (the same value CI passes, `origin/<target>`) in the environment of every spawned task, so that `ratchet`, `host-safety` and `check-skill-versions`, which compute their own merge-base from it, diff against the same base as the selection. (f) If the target ref or the merge-base cannot be resolved (no `origin`, shallow clone), the wrapper SHALL print a notice naming the reason and run every fast-tier capability, never none. (g) An empty changeset runs the always-run capabilities only. Acceptance: tests on `mkdtemp` git repositories prove selection for a changeset touching only `docs/`, only `specs/`, only `taskfiles/`, only `artifacts/`, and empty; the notice of (f); and that an uncommitted file does not change the selection.
9. **R9 (fast tier, budget, record).** The fast tier SHALL be an explicit list of capability ids, committed in `ci/pre-push-tier.json` as `{ "<id>": <measured seconds on the reference machine>, ... }`, and SHALL be a subset of the capabilities that have a `ci:<id>` task. Admission rule: a capability is admitted only if it is deterministic, needs no container, network, Windows host or secret, and its measured time is at most 20 s alone. The initial list is: `check-taskfile-tree`, `check-taskfile-commands`, `lint-specs`, `lint-markdown`, `markdown-links`, `repository-scan`, `lint-typescript`, `ratchet`, `host-safety`, `path-ownership`, `check-skill-versions`, `check-description-length`, `check-agents-size`, `check-rules-size`, `check-comment-size`, `docs-index`, `cli-matrix-fresh`, `test-wiring`, `check-ci-parity`, `gitlab-ci-check`, `component-drift`, `frontmatter`; the PLAN confirms each against its measured time and drops any that fails the admission rule, recording the reason in the evidence table of R17. `ci:pre-push` SHALL run the selected tasks concurrently with a pool of `min(4, available cores)`, buffer each task's output and print it only on failure (a one-line status with the duration otherwise), and print a timing summary. The total wall-clock budget is 60 s on a typical change (a changeset of at most 20 files touching docs, specs, scripts or taskfiles), on the reference machine (macOS, warm `node_modules`). Baseline measurements on `main` (single task, seconds): `spec:lint` 4, `lint-markdown` 4, `lint-ts` 4, `ratchet` 1, `host-safety` 1, `path-ownership` 1, markdown-links suite 1, each `check-*` below 1, component drift check 1; about 20 s sequential for the checks alone. Measured on the same tree, the self-test suites that the CI commands of R3 also run add: `spec-linter-*` 18, `check-path-ownership` 10, `check-ratchet` 8, `check-stray-scan-wiring` and `ci-cache-guard-scan` group 6, `check-host-safety` 5; about 47 s sequential, which is why the pool is required and why exact CI commands fit the budget only when run concurrently. Budget guard: a test SHALL fail when the sum of the recorded seconds of the always-run capabilities exceeds 60 times the reference pool size, a committed constant fixed at 4 and independent of the machine core count (the run-time pool stays `min(4, available cores)`), or when a capability of the tier list has no recorded time, so an admission without a measurement fails in CI; at run time the wrapper prints a warning line (without failing) when the wall-clock exceeds 60 s. Re-measurement is a manual step recorded in the PR (R17), and a capability whose recorded time exceeds 20 s is removed from the tier. Acceptance: the guard test, and the evidence table of R17.
10. **R10 (excluded families).** The following families SHALL stay CI-only, each for the reason given, and no `ci:<id>` task SHALL be defined for them by this spec: end-to-end and container jobs (`e2e`, `setup`, `extension-install`: need Docker and long runs); MCP daemon and chroma jobs (`mempalace`, `chroma-mcp`, `mempalace-session-check`, `mempalace-transcript*`: need services and ports); setup and install golden, oracle and differential suites (`setup-oracle`, `setup-differential`, `setup-modules-ts`, `install-ts*`, `build-components-ts*`, `extension-builders-ts*`: minutes of CPU, matrix over Node versions); every `windows-*` capability (needs a Windows host); release, packaging and pages jobs (`release*`, `packaging-modules-ts`, `pages-deploy`); usage-capture and worktree-guard suites (`usage-*`, `worktree-guard*`); `figure-labels` (needs `tesseract`); `changeset-coverage` and `changeset-coverage-test` (the exhaustive net, daily). A fast-tier capability that later grows past the admission rule moves here in the same change. Acceptance: the guard of R4 reports no `ci:<id>` for an excluded id and no missing task for an admitted one.
11. **R11 (pushed refs).** The hook receives `<local ref> <local sha> <remote ref> <remote sha>` lines on stdin (git pre-push protocol) and the remote name and URL as arguments. The hook SHALL pass the lines to `ci:pre-push` through the environment variable `CREWRIG_PRE_PUSH_REFS` and the remote as arguments after `--`; a manual `task ci:pre-push` with the variable unset behaves as a push of `HEAD`. Per line: (a) a delete (local sha all zeros) is skipped with a one-line notice; (b) a new branch (remote sha all zeros) and an existing branch are both handled the same way, with the merge-base of the local sha and the target ref (R8); (c) a tag ref is skipped with a notice; (d) several refs: the changeset is the union of the per-ref diffs, and the checks run once. The checks run on the working tree, so only a ref whose local sha equals `HEAD` can be checked: any other pushed ref SHALL be reported as `not checked: <ref> is not the checked-out commit` and SHALL NOT fail the push (CI covers it). If the working tree is dirty, the wrapper prints a notice that the checks see uncommitted changes. If no ref remains to check, the hook exits 0 with a notice. Acceptance: tests with fixture stdin cover each case.
12. **R12 (spec 0168 R1 is a merge gate, not a push gate).** Pushing a spec branch whose spec is still `status: draft` is normal, because the PR is a Draft PR. `ci:pre-push` SHALL set `CREWRIG_PR_DRAFT=true` in the environment of the `ci:lint-specs` task and of no other task, so spec 0168 R1 (and only R1, per spec 0168 delta-01 R8) is skipped, while every other spec-linter rule stays enforced. The hook SHALL NOT read the PR draft state from the forge (no network, no authentication). Acceptance: a test with `mkdtemp` fixtures runs the pre-push `ci:lint-specs` path twice: a spec with `status: draft` passes, and a spec with a different violation (a missing required frontmatter field) still fails, with the same environment.
13. **R13 (fail closed, never silent).** The hook and the wrapper SHALL exit non-zero, with a message naming the cause and the fix, and SHALL NOT pass silently, in each of these cases: (a) `node_modules` is absent from the checkout the hook runs in, or lacks a binary a selected task needs (the preconditions of R5): message `run task lint-bootstrap`; (b) `task` is not on `PATH`: message naming the installation page. The Task floor is not checked by the hook or the wrapper: it is enforced by `version: '3.39'` in every Taskfile (spec 0278 R8), Task fails with its own message and the hook relays its status and output; (c) `node` is older than the 24 floor: the hook tests `typeof process.getBuiltinModule === 'function'` first (R14) and fails with a message naming the Node 24 floor, and `ci:pre-push` runs `node scripts/lib/node-floor-guard.js` as its first command (R8), before `scripts/ci-pre-push.ts`, and relays its message; if `node` is absent altogether the shebang line fails in the shell before any code of ours runs and the push is blocked with the shell's message (documented, accepted); (d) the capability file or a Taskfile cannot be read, or a glob is unsupported: message naming the file; (e) any internal error of the wrapper. The only success paths without running checks are the explicit no-op notices of R11 and R18. The hook SHALL never run `npm ci`, `npm install` or any network command. Acceptance: tests with a fixture checkout lacking `node_modules`, a fixture `PATH` lacking `task`, and a forced internal error, each asserting a non-zero exit and the message.
14. **R14 (hook form and install).** The hook is the versioned file `.githooks/pre-push`, an extensionless executable (mode 100755) whose first line is `#!/usr/bin/env node`. Decision and reasons: `scripts/lib/ts-scope.ts` `isShellFile` flags a tracked file that ends in `.sh` or whose first line is a `sh`/`bash` shebang, and `ci/shell-allowlist.txt` is shrink-only, so a `#!/bin/sh` hook would fail `task ratchet` with no admissible exemption; a `*.js`/`*.mjs`/`*.cjs` file needs an entry in `ci/js-exceptions.txt`, which admits only the `node-floor-guard` and `tool-config` categories; an extensionless file with a `node` shebang is neither, so it passes the ratchet without a baseline entry. It works on Windows, macOS and Linux: Git for Windows runs hooks through its own `sh`, which honours the shebang, and `node` is already a prerequisite of every repository script. The file is written in dependency-free plain JavaScript that uses `process.getBuiltinModule` (no `require`/`import` form, so it behaves the same whatever the package module type), is at most 45 lines, and does exactly six things, in this order and no other (R18 refers to this list): (1) test `typeof process.getBuiltinModule === 'function'` and, when absent, print a message naming the Node 24 floor and exit non-zero before using any other API; (2) resolve the checkout with `git rev-parse --show-toplevel` run from the current directory; (3) when that toplevel has no `taskfiles/ci.yml` (not a CrewRig checkout), exit 0 with a notice; (4) run `task ci:pre-push -- <remote> <url>` with that directory as the working directory and `CREWRIG_PRE_PUSH_REFS` set from stdin, (5) relay its output and exit status; (6) fail with the R13 message when `task` is absent (its only Task duty). All logic lives in `scripts/ci-pre-push.ts`. The PLAN SHALL verify that the file passes `task ratchet`, `task lint-ts` (the file is outside the TypeScript scope by extension), `oxfmt`/`oxlint` scope and `scripts/check-path-ownership.ts`. Acceptance: those four commands pass with the hook committed; the ratchet baseline files are not edited.
15. **R15 (enablement, scope, idempotence).** `ci:hooks-install` SHALL run `git config --local core.hooksPath .githooks` from the repository root; `ci:hooks-uninstall` SHALL run `git config --local --unset core.hooksPath` only if its current value is `.githooks`. Scope: the only thing written is the local configuration of this repository (`.git/config`, shared by its worktrees). The tasks SHALL refuse with a message and a non-zero exit outside a CrewRig checkout (the check: `.githooks/pre-push` and `taskfiles/ci.yml` exist at the toplevel of the current repository), SHALL never use `--global` or `--system`, SHALL never write under the user's home directory and SHALL never touch another repository. They are idempotent: a second run changes nothing and reports `already enabled`. If `core.hooksPath` already holds another value, `ci:hooks-install` SHALL refuse, print the value, and change nothing unless `FORCE=true`. Decision on setup: the repository setup scripts (`scripts/setup-*-interactive.ts`, `task install-deps`) SHALL NOT call `ci:hooks-install`, because they run for adopters and in directories that are not a CrewRig development checkout; enablement is explicit, one command, documented in `DEVELOPMENT.md` and in the contributor onboarding path of `CONTRIBUTING.md` if it names developer setup. The task `ci:hooks-status` (prints the current `core.hooksPath`, cheap) is included. Acceptance: tests on `mkdtemp` git repositories prove install, idempotence, refusal on a foreign value, refusal outside a CrewRig checkout, uninstall, and that `$HOME` and `git config --global --list` are unchanged (the test runs with `HOME` pointed at a `mkdtemp` directory and `GIT_CONFIG_GLOBAL` set to `/dev/null`).
16. **R16 (CI wiring).** Every new test and guard (R4, R8, R9, R11, R12, R13, R14, R15, R17) SHALL be wired into CI in `.github/workflows/build.yml` and `ci/ci-capabilities.yml`, with `.gitlab-ci.yml` regenerated by `node scripts/build-ci.ts` (never hand-edited), so that `scripts/check-test-wiring.ts`, `scripts/check-path-ownership.ts` and `scripts/check-ci-parity.ts` pass. The guard of R4 and its tests belong to the existing `check-taskfile-tree` capability or to a new capability the PLAN names; the paths filter of the owning capability SHALL list `taskfiles/**`, `ci/ci-capabilities.yml`, `ci/pre-push-tier.json`, `.githooks/**` and the new scripts. `.githooks/**` SHALL be owned by a capability's `paths:` or listed in `ci/path-ownership-exemptions.txt` with a reason naming the capability that exercises it. The edits of R6 to `ci/ci-capabilities.yml` SHALL be reflected in `build.yml`. Acceptance: the three commands above pass on the PR.
17. **R17 (acceptance evidence).** The PR SHALL carry (a) a deterministic, mutation-style replay and (b) a one-time measured evidence table. (a) The replay, in a committed test, takes the failure classes of the last 60 failed `build.yml` runs analysed on #1761 (spec lint violations other than R1, Markdown lint, Markdown links, test wiring, CI parity, component drift, changeset coverage, path ownership, TypeScript format and typing, skill version bump) and, for each class, creates a minimal violation in a `mkdtemp` copy of the relevant fixture tree, runs the selection and the `ci:<id>` task of R8 against it and asserts a non-zero exit naming the capability. Every mutation SHALL operate only on paths the test created with `mkdtemp`; a test SHALL NOT remove or restore a path it did not create (`scripts/check-host-safety.ts`). Classes that are checked by an exhaustive net only (changeset coverage) SHALL be stated as such, with the fast-tier capability that blocks the same class named, or be reported as not blocked locally with the reason. (b) The table, one row per replayed class, SHALL give the capability id, the command that caught it, the wall-clock of that task and the end-to-end wall-clock of `ci:pre-push` on a typical change, measured on the reference machine and re-measured in a second environment (a Linux container with warm `node_modules`) because timings and paths differ between machines. Acceptance: the replay test passes and the table is in the PR description; every class reported as not blocked is justified.
18. **R18 (worktrees).** `core.hooksPath` is configuration shared by every worktree of the repository. The hook SHALL resolve the checkout it runs in at run time, with `git rev-parse --show-toplevel` from the working directory git gives the hook, and SHALL run `task ci:pre-push` from there; it SHALL NOT use a path baked in at install time and SHALL NOT use `core.hooksPath` as an absolute path. In a fresh worktree without `node_modules` the push SHALL fail with `run task lint-bootstrap` (R13a), never pass. The no-op outside a CrewRig checkout is duty (3) of the hook's list in R14: the hook exits 0 with a notice when the toplevel has no `taskfiles/ci.yml`, since `core.hooksPath` could have been set to a relative `.githooks` that exists in a repository that is not CrewRig. Acceptance: a test with two `mkdtemp` worktrees, one with and one without `node_modules`, sharing one `core.hooksPath`, proves each runs in its own toplevel and the bare one fails.
19. **R19 (CLI symmetry and escape hatch).** The hook SHALL apply to every agent that pushes with `git` (Claude Code, Gemini CLI, GitHub Copilot CLI, Antigravity CLI) with no per-CLI wiring, no per-CLI script and no per-CLI hook file. A row SHALL be added under `docs/cli-matrix/rows/` stating that the four CLIs are symmetric through native git and that no CLI integration point exists for it (the row source records the source of truth, `.githooks/pre-push`, `scripts/ci-pre-push.ts`, `taskfiles/ci.yml`, and the escape hatch), and `docs/cli-matrix.md` SHALL be rebuilt with `task cli-matrix:build` in the same diff; the PLAN picks the row id by the style of the recent rows. The documentation SHALL state: `git push --no-verify` skips the hook; CI stays authoritative and the hook is a convenience, not a gate; how to enable it (R15); the 60 s budget; the Node 24 and Task 3.39 floors. Documentation to update: `DEVELOPMENT.md` (a section *Pre-push guard*), a short page `docs/pre-push-guard.md` with its docs-index entry (spec 0147 `docs-index`), `docs/ci-reference-format.md` if it names the `ci:` task naming rule, and `CONTRIBUTING.md` if it names developer setup. `AGENTS.md` SHALL be edited only if a rule binding agents is added, and then by a single line pointing at the docs page, because `scripts/check-agents-size.ts` bounds it. Acceptance: the matrix row exists and `task cli-matrix:check` passes; the docs pass `task lint-markdown` and `markdown-links`.
20. **R20 (Windows command rule and tree invariants).** Spec 0278 invariants hold: `scripts/check-taskfile-tree.ts` passes, the name-set baseline is extended with the new names (R1), and every command in `taskfiles/ci.yml` satisfies the spec 0266 Windows-command rule enforced by `scripts/check-taskfile-commands.ts` (no forbidden utility such as `jq`; the wrapper and tests are Node scripts). `ci:*` tasks reference the repository through `{{.REPO_DIR}}` as `taskfiles/lint.yml` does, never `TASKFILE_DIR`; raw commands written in `taskfiles/ci.yml` use `{{.REPO_DIR}}/` for repository paths (stripped by normalisation step (c) of R3); and every `- task:` call from `taskfiles/ci.yml` to a task of another file uses the colon-anchored global form of R2. Acceptance: the existing guards pass unchanged apart from the baseline extension.

## Scenarios

**Scenario:** a Markdown-only change runs only what it can affect

Given a branch whose commits touch only `docs/foo.md`
When `git push` runs the hook
Then the always-run capabilities and the capabilities whose `paths:` match `docs/foo.md` run, the others are not started, and the run ends within the budget

**Scenario:** a draft spec branch pushes

Given a branch with a spec file of `status: draft` and no other violation
When the hook runs `ci:lint-specs`
Then it exits 0, while the same file with a missing required frontmatter field exits non-zero

**Scenario:** a fresh worktree fails closed

Given a worktree with no `node_modules` and `core.hooksPath` set to `.githooks`
When `git push` runs the hook
Then the push fails with a non-zero exit and the message `run task lint-bootstrap`

**Scenario:** drift between a task and its CI job is caught

Given a `ci:lint-markdown` that drops `--ignore communication`, or a capability whose command changes without the task
When the parity guard runs
Then it fails naming the capability id and the first differing command

**Scenario:** an unrelated repository is not touched

Given a git repository that is not a CrewRig checkout
When `ci:hooks-install` runs there
Then it refuses with a non-zero exit and writes nothing

**Scenario:** a push of a new branch with a delete in the same push

Given `git push origin new-branch :old-branch`
When the hook receives both lines
Then `old-branch` is skipped with a notice and `new-branch` is checked against the merge-base with `origin/main`

## Out of scope

- A `ci:<id>` task for every CI job (the later work package of epic #1761, WP-C), and any change of a CI job's engine logic beyond the `lint-markdown` convergence of R6 and the wiring of R16.
- Making the hook a required gate, running it in CI, or removing `--no-verify`.
- Running slow families locally (R10), including an emulation of the GitHub runner.
- Installing the hook for adopters' repositories or from the setup scripts (R15).
- Any change to the spec linter rules, to spec 0168, or to `build.yml` pull-request types (#1762).
- Auto-fixing: the hook never rewrites a file (no `fix-markdown`, no `format-ts:fix`).
- A global `core.hooksPath`, a hook for `pre-commit`, `commit-msg` or any other git event.

### Risks

| Risk | Mitigation |
|---|---|
| The hook becomes slow and developers habitually use `--no-verify` | Fast tier only, pool, measured budget, run-time warning above 60 s, admission rule capped at 20 s per capability (R9) |
| Exact CI commands include self-test suites that add about 47 s of CPU | Concurrent execution; the budget test works on recorded wall-clock sums per pool (R9) |
| The task and its CI job drift apart over time | R4 compares the resolved command lists mechanically in CI; R5 shares one provisioning definition |
| The hook passes silently in a state where it checks nothing | R13 enumerates every fail-closed case and R18 the only no-op; each is tested |
| A hook that works only on the author's machine | R14 form passes the ratchet and runs under Git for Windows `sh`; evidence re-measured in a second environment (R17b) |
| The checks see the working tree, not the pushed commit | R11 reports unchecked refs and a dirty tree explicitly; CI remains authoritative |
| The selection under-selects because of a path filter gap | The selection reuses the `paths:` filters that `path-ownership` and `changeset-coverage` already keep complete; no new filter exists to be wrong |
| `core.hooksPath` collides with an existing local setting | R15 refuses unless `FORCE=true` and reports the current value |

### Alternatives considered

- **Husky.** Rejected: a Node dependency and an install step that writes to the repository, and a second mechanism beside Task; the issue requires no new dependency.
- **Lefthook.** Rejected: a Go binary to install on every machine and a second configuration file that would have to track `ci/ci-capabilities.yml`.
- **The `pre-commit` framework.** Rejected: Python dependency, its own environments, and a configuration that duplicates the check list; it also targets the commit event, which is too frequent for a 60 s budget.
- **Running the real jobs with `act`.** Rejected: needs Docker, is far above the budget, and does not run the Windows and macOS-specific parts faithfully.
- **A Node-only hook without Task.** Rejected: it would re-implement the `ci:<id>` indirection that WP-C extends to every job and would lose the single entry point `task ci:pre-push` that a human can run by hand; the extensionless hook (R14) keeps only the minimal Node bootstrap, which is the part that must work before Task is known to be present.
- **A `#!/bin/sh` hook.** Rejected: flagged by `isShellFile`, fails the shrink-only shell ratchet, and the ratchet forbids an exemption (R14).
- **A `.mjs` or `.js` hook behind a one-line stub.** Rejected: needs an entry in `ci/js-exceptions.txt`, which admits only two categories.
- **`core.hooksPath` set globally (`git config --global`).** Rejected: it would affect every repository of the user and adopters' repositories, which R15 forbids; local only.
- **Setting the hook from the repository setup scripts.** Rejected: setup runs for adopters, outside a development checkout (R15).
- **Reading the PR draft state from the forge.** Rejected: needs network and authentication at push time; `CREWRIG_PR_DRAFT=true` set unconditionally for `ci:lint-specs` is deterministic, and R1 is a merge gate (R12).
- **A separate pre-push command list.** Rejected: a second source of truth for CI commands; R3-R4 make the CI reference the single source.

## Open questions

The PLAN confirms two points of mechanism: that `scripts/lib/ci-parity/reference-read.ts` exposes the `pull-request` trigger `paths:` list through `CapRecord`/`TriggerRecord` without a new parser (otherwise a minimal accessor is added there, not a second reader), and that the extensionless hook is classified as neither shell nor JavaScript by `scripts/lib/ts-scope.ts` and by the path-ownership classes (R14); if either does not hold, the PLAN reports it as a `spec`-class finding before DEV.
