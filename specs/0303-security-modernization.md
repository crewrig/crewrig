# Modernize the security skill and agent, and give the secrets check one engine

## Intent

The `security` skill and the `security` agent are rewritten to the skill authoring standard (`docs/skill-authoring-standard.md`), as wave 3c of the CI and security modernization that followed the `github-actions` (spec 0300) and `gitlab-ci` (spec 0301) rewrites. Two steps whose outcome is fixed become bundled scripts: the shape check of a findings report, with a location that must resolve to a real file and line, and the dependency audit, which detects the ecosystem, runs its native audit command and says plainly when it could not. The secrets-exposure check, today written twice with the same skeleton and different patterns in `github-actions` and `gitlab-ci`, becomes one engine whose platform-specific parts are data, and the observable behaviour that the existing oracle suites pin stays identical. The agent states when to delegate to it and keeps only its role and its boundary. The effect is measured on frozen cases, not asserted.

## Requirements

1. **R1 (order of work).** The work SHALL land as one implementation pull request whose commits are ordered: first the `evals/` of the `security` skill (cases and fixtures) with no change to the skill or the agent; then a baseline measurement on the unchanged skill, committed; then the real captures of R11 as fixtures; then the scripts, the engine, their tests and the rewrites; then one commit of REVIEW fixes; then the final measurements of R5. Cases and fixtures SHALL stay byte-identical after the first commit. Because the eval content hash covers `SKILL.md`, `scripts/`, `references/` and `assets/`, every edit of those paths after a measurement makes the committed `evals/results.json` of that skill stale, so REVIEW fixes SHALL be batched into one commit before the final measurements, never measured one by one.
2. **R2 (cases of the security skill).** `artifacts/core/skills/security/evals/evals.json` SHALL be valid under the eval schema of `docs/skill-evals.md` and SHALL hold at least five evals, each asking for a file to be written (for example `security-review.md`), the prompt naming that file. The fixtures of an eval SHALL carry the changed files whole under `evals/files/` (for example `src/handler.js`) next to any `.diff`, and the prompt SHALL tell the run to cite lines of those whole files, so that the `Where:` values of its report resolve in the workspace. The cases: a review of a supplied change to an HTTP handler that interpolates a request value into an `ORDER BY` clause and joins a user-supplied path to a directory; a supplied change that adds a literal API key (the correct report is a `BLOCKER` finding whose `Fix:` line says to read the key from an environment variable or a secret store and to rotate the exposed key, and whose `Evidence:` line shows the code with the key masked, at most four characters followed by asterisks); a dependency upgrade supplied as a manifest diff with a changelog excerpt that holds a major bump; a supplied change whose only candidate issue is a parameterized query, where the correct report is `No findings.` followed by an `Examined:` line; and a threat model request for a small file-upload endpoint. Every expectation SHALL quote a whole line of the written file, or a literal of the same size, that holds at least 12 non-whitespace characters and at least 12 letters and digits (a runner evidence rule: the normalised match counts letters and digits only), and SHALL name that line: the finding line `1. [BLOCKER] ...` in full, the full `Where:` line that names a fixture file and a line number, the full `Fix:` line, the full `Examined:` line, the line that names the trust boundary of the upload endpoint. A bare `[BLOCKER]` (9 characters) or a bare `No findings.` (11 characters) is not an anchor; the case author SHALL count the characters of every anchor. No expectation SHALL be phrased on an absence alone, on a short token, or on how the output was produced; a secondary clause may add that the fixture's full key does not appear, never in place of a positive quote. A `file_exists` or `file_contains` check, when used, SHALL point at a file that the prompt itself tells the run to write.
3. **R3 (no forge, no script check).** No eval prompt SHALL ask the agent to create, edit, comment on or close a forge artifact, to run a real dependency audit against a network, or to scan a real repository. Fixtures SHALL be plain files under `evals/files/`. No eval SHALL use an `exit_code` check on a bundled script, so the same cases measure the skill before and after the scripts exist.
4. **R4 (probes).** The file SHALL carry at least ten trigger probes, at least 40 percent positive and at least 40 percent negative. The positives SHALL include a threat-model request phrased without the word "security", a dependency upgrade review, a leaked credential in a diff, and a deserialization or token-validation review. The negatives SHALL be near-misses that share vocabulary, one of each of these kinds at least: authoring or hardening a GitHub Actions workflow, authoring a GitLab pipeline, writing a pull request description, producing a verdict on a pull request, a refactor with no trust boundary, and a plain question on how to install a package.
5. **R5 (measurement).** For the `security` skill the contributor SHALL measure the unchanged skill (baseline, committed before the rewrite) and the rewritten skill (final) with `task skill-evals -- security`. `main` holds no committed `evals/results.json` for this skill, so the runner prints `base=n/a`: the comparison is manual and the rewrite is kept only when the final eval pass rate is at least the baseline minus the runner tolerance (0.05) and the final status is `pass`. For `github-actions` and `gitlab-ci`, whose hashed content changes under R6 and R14, the contributor SHALL make one final measurement each with `task skill-evals -- <skill>` on the frozen cases of that skill (no case, fixture or probe edit), the base figure being the `evals/results.json` committed at the merge-base with `main`; the printed `base=` SHALL equal that file's `eval_pass_rate`, and on a difference or an `n/a` the contributor SHALL stop and report instead of spending a further run. A sibling is kept when its final status is not `regression` and is `pass`. At most four paid measurements SHALL be made for each of the three skills (for `security`: baseline, final and at most two re-measurements; for each sibling: the final and at most three re-measurements), the figures of every run SHALL be reported on the logbook (pass rates, probe results, cost, run counts, and per-expectation failures), and the `evals/results.json` of the final non-mock run of each skill SHALL be committed. A probe failure SHALL be fixed by revising the description before the body. The committed results of both siblings are stale from the first edit of R6 until their final run, which is expected. `github-actions` and `gitlab-ci` both stand at 5 of 6 evals (0.833), so one extra miss falls under 0.80: that case consumes the re-measurement budget, and since both siblings change only by a byte copy and a version bump their measurements add no information about the change and expose it to judge noise, which is why each is limited to the one final run plus the re-measurements the noise forces; if the work of #1942 lands first, the measurement is made once for the combined content under R14, and when a skill is still below the bar after its four runs the figures go to the user for decision, with no further run and no check bypassed.
6. **R6 (one secrets engine: where it lives and how each skill gets it).** There SHALL be one source of the secrets-exposure check: `artifacts/core/skills/security/scripts/check-secrets-exposure.ts`, a single TypeScript file with no import, that holds the shared skeleton (target resolution, line scan, report, exit codes) and one profile per platform, `github` and `gitlab`, each profile carrying that platform's patterns, messages, usage text and target discovery. `artifacts/core/skills/github-actions/scripts/check-secrets-exposure.ts` and `artifacts/core/skills/gitlab-ci/scripts/check-secrets-exposure.ts` SHALL be committed copies of that file at the same relative path in their skill, identical to it byte for byte except one marked line that declares the default platform (`"github"` in `github-actions`, `"gitlab"` in `gitlab-ci`, none in `security`). The patterns SHALL NOT move to separate pattern files, because a script is one file with no import (rule 1 of the script contract) and a pattern file would not survive the copy of a skill directory. No shared-script mechanism SHALL be added to the build, and neither sibling SHALL call the file of another skill. A test SHALL fail, naming the file and the first differing line, when a copy differs from the canonical file outside the marked line, and SHALL pass when only the marked line differs. The reasons are recorded under the Open questions, so that the next maintainer can see the rejected routes.
7. **R7 (the engine keeps the pinned behaviour, byte for byte).** With no new option, each copy SHALL behave exactly as the script it replaces for every argument form the legacy script accepts or rejects today: detection, text, streams, exit codes (`0` clean or nothing to scan, `1` a finding or a bad target, `2` usage) and files written, including the legacy differences between the two (the `github` profile answers `--help` anywhere among its arguments and scans `<dir>/.github/workflows` when it exists; the `gitlab` profile answers it only as the sole argument and scans `<dir>/.gitlab-ci.yml` plus the YAML under `<dir>/.gitlab/`; their usage, empty-scan and missing-target messages differ). Every test and golden file of spec 0258 and of the specs 0300 and 0301 that names `check-secrets-exposure` (the oracle, differential, layouts and mutation suites with their goldens, the callers and callers-sweep checks, the Windows cases, and the `github-actions` contract, copied and validate-pipeline tests and the `gitlab-ci` baseline, legacy-flags and copied tests) SHALL pass unchanged: no golden is regenerated, no existing test or case table is edited, and tests are only added. The regular expression text that the mutation suite replaces (`set${SP}+[-+]x(${SP}|$)`) SHALL stay verbatim and occur exactly once in the `github-actions` copy, because the unchanged mutation test asserts that single occurrence on the pristine file: the profiles keep distinct whitespace constants (`SP` for `github`, `WS` for `gitlab`), and the profile layout SHALL respect it. The mutation suite runs unchanged against that copy. The engine SHALL NOT gain `--json` or exit `3`, because the `gitlab-ci` baseline goldens pin `--json` and `--json <file>` as usage errors (the `github-actions` contract test only runs the one-argument form, so it pins nothing about `--json`; a github `--json` golden MAY be added before the copy replaces the script, as a test addition); `--help` and `SKILL.md` of `security` SHALL say so. The approach follows the precedent of the two sibling specs, which kept every existing exit code and message and added flags only, because the spec 0258 oracle closes its list of deviations.
8. **R8 (the only new option: `--platform`).** The engine SHALL accept `--platform <github|gitlab>` and `--platform=<github|gitlab>` before its one target. The pair is removed from the arguments and the named profile then applies its own rules to the remaining arguments exactly as it would have without the option. When `--platform` is present, `--help` anywhere in the arguments takes precedence: it prints the usage and exits `0` before the value is validated (`--platform bitbucket --help` and `--platform --help` print the usage, exit `0`). Otherwise an unknown value, a missing value or a repeated option is a usage error, exit `2`, naming the two valid values. In the `security` copy, which has no default platform, an invocation without `--platform` is a usage error, exit `2`, whose message names the option and its values (never a guess from the target); its `--help` as the sole argument prints the usage of the engine, names both platforms and the legacy exit codes, and exits `0`. In the two sibling copies `--help` SHALL remain byte-identical to the legacy text, which therefore does not mention `--platform`: the option is documented in the `security` skill, and a sibling copy still accepts it.
9. **R9 (security-finding script).** The `security` skill SHALL bundle `scripts/security-finding.ts` under the script contract of the standard: a single TypeScript file for Node.js 24, no import, `--help`, `--json` object `{ok, data, findings}`, exit codes `0`, `1`, `2`, `3`, no network call, no write. It reads one report from a file path or from `-` for standard input and checks it against the output format of the skill: numbered findings of the form `N. [SEV] <summary>` followed by the fields `Where:`, `Threat:`, `Evidence:` and `Fix:`, a field value possibly continuing on indented lines. `--root <dir>` (default the working directory) is the directory that `Where:` values resolve against. It SHALL report an error finding for each of these rules: `severity-missing` (no bracketed severity), `severity-unknown` (a bracketed word outside `BLOCKER`, `HIGH`, `MED`, `LOW`, `INFO`, the message listing the five), `field-missing` (a required field absent, naming it), `placeholder` (a field whose value is still template text in angle brackets, so that the unmodified template cannot pass), `where-format` (a value that is not `<file>:<line>` or `<file>:<first>-<last>`), `where-file-missing` (the file does not exist under the root or is not a regular file), `where-line-out-of-range` (a line below 1 or past the last line of the file, or a range whose last line is below its first or past the end), `where-outside-root` (a path that resolves outside the root), and `numbering` (the numbers are not 1 to N in order). Every finding carries the finding number and a message that states the fix. A report with no numbered finding SHALL pass only when it holds the line `No findings.`; otherwise it SHALL report `no-findings-block`, so that a wrong input file or an empty one cannot pass for a clean review. A missing or unreadable report, or a root that is not a directory, is exit `3` with rule `precondition`; a usage error is exit `2`. `data` states the number of findings checked and the count per severity. When the reviewed input is a diff, the finding cites the path of the post-image from the `+++` header and a line of the new-file side of the hunk, in a checkout that holds that file; a path that exists only in the diff is `where-file-missing`. The script does not check that the quoted evidence occurs at the cited line.
10. **R10 (dep-audit script).** The `security` skill SHALL bundle `scripts/dep-audit.ts` under the same contract: `dep-audit.ts [--root <dir>] [--ecosystem <npm|pip>] [--fail-on <low|moderate|high|critical>] [--timeout <seconds>]` (default root the working directory, default `--fail-on high`, default timeout 60 seconds). It SHALL detect the ecosystems at the top level of the root only: `npm` from `package-lock.json` or `npm-shrinkwrap.json` (a `package.json` alone is the cause `no-lockfile`), and `pip` from `requirements.txt`. A manifest or lockfile of another ecosystem that it recognises (`pnpm-lock.yaml`, `yarn.lock`, `go.mod`, `Cargo.lock`, `poetry.lock`, `pom.xml`, `Gemfile.lock`, `composer.lock`) SHALL yield a warning finding `unsupported-ecosystem` stating that those dependencies were NOT audited and naming the native tool to run by hand. For each audited ecosystem it SHALL run the native command with a fixed argument vector and no shell (`npm audit --json --package-lock-only --ignore-scripts` and a `pip-audit` vector fixed by R11), looked up on `PATH` only so that tests substitute stubs, never with a command that fixes or writes, and never in a way that installs, builds or executes project code (a build backend or install hook of the reviewed project is code execution by the file under review), and SHALL put the child in its own process group and kill the group at the timeout, so that no process outlives the script. The verdict of each ecosystem is `clean`, `vulnerable` or `not-audited` with a cause among `tool-missing`, `timeout`, `offline`, `unrecognized-output`, `no-lockfile`, `unpinned` (a requirements file that the non-building mode cannot read) and `unsupported`; it SHALL be recognised from the exit code together with the parsed output of the real captures of R11, never from the exit code alone, because npm exits `1` both for a vulnerability and for a failed query, and any output it cannot classify is `unrecognized-output`, never `clean`. A vulnerable verdict yields one finding `vulnerable-dependency` per advisory, stating the package, the version, the advisory identifier or title, the native severity (an advisory without one counts as at or above the threshold) and the fixed version when the tool reports one, and it says that reachability was not assessed. A finding is an error when its severity is at or above `--fail-on` and a warning below it. A `not-audited` ecosystem that is supported yields an error finding `precondition` naming the cause and stating that the dependencies were NOT audited. The exit code is `1` when any `vulnerable-dependency` error exists (a finding always wins, and `data` still lists every ecosystem and its verdict), else `3` when any `precondition` error exists or when manifests were detected and none was audited, else `0`; a root with no manifest at all exits `0` with a warning `nothing-to-audit` and an empty `audited` list in `data`. Arguments are checked first (exit `2`), then the root (exit `3`), and only then the tools. `--ecosystem` restricts the run, an unknown name is a usage error, and a named ecosystem with no manifest at the root is exit `3`. The script is POSIX-only: it spawns the child in its own process group and looks the tool up without a shell, which `npm.cmd` shims on Windows defeat, so on `win32` it exits `3` with a `precondition` finding of cause `unsupported-platform` after the argument check and before any tool is looked up; `--help` and `SKILL.md` say so, and an additive Windows case of the Windows skill-script proof asserts it.
11. **R11 (captures before the script).** Before `dep-audit.ts` is written the contributor SHALL capture the real output of `npm audit --json --package-lock-only` for a clean project, a project with a known advisory and a run with no network, and of `pip-audit` on a requirements file for the same three situations, record the tool versions, and commit the captures as fixtures that the test stubs replay, with no private path, host or user name in them. The `pip-audit` vector SHALL be chosen in this step so that it does not install or build: the capture records whether the default invocation builds, and the vector uses the modes that avoid it (for example `--no-deps --disable-pip`, which needs a fully pinned file), verified with a requirements fixture that names a source-only package whose build hook would write a marker file, the marker being absent after the run; when no vector that cannot build exists, `pip` SHALL degrade to `not-audited` with cause `unsupported` and ship no audit command. The recognition rules of R10 SHALL be written from those captures; a capture that disagrees with the rules of R10, or an ecosystem whose tool cannot be run to make a capture, SHALL be raised as a spec finding and that ecosystem SHALL NOT ship from documentation alone.
12. **R12 (standard amendment).** The implementation pull request SHALL amend rule 5 of the script contract in `docs/skill-authoring-standard.md` by one sentence appended after the forge-query sentence that spec 0301 added, as an explicit exception to the no-network sentence, so that rule 5 ends: "A script that writes nothing to a forge makes no network call. A script that writes nothing to a forge may make a read-only query through the forge's own command-line tool, bounded by a timeout, and degrades to exit `3` when the query cannot run, never to success. As a further exception to the no-network rule, a script that writes nothing MAY run the audit command of a package manager, with a fixed argument vector, no shell and a timeout, provided the invocation neither installs, builds nor executes project code nor writes a file of the project, and it degrades to exit `3` when the command cannot run, never to success. A script never stages, commits or pushes." That sentence is the only change to the standard, the approved spec 0293 is not edited, and read-only is a property the spec guarantees of the invocation (R10, R11), not an assumption about the tool. `dep-audit.ts` documents the network use of the native tools in its `--help`, and `SKILL.md` says that it queries a package registry.
13. **R13 (script tests).** The two new scripts and the engine SHALL have automated tests that run with no network and cover: for `security-finding.ts`, the success path, every rule of R9 with its compliant counterpart, the unmodified template of the skill (which SHALL report findings), standard input, `--root`, a path that escapes the root, a range, a report with `No findings.`, an empty report, the usage error, the precondition, the `--json` shape on each exit and `--help`; for `dep-audit.ts`, driven only through stubs on `PATH`, a clean, a vulnerable (one at and one below `--fail-on`) and a missing-tool case per ecosystem, an offline capture (exit `3`, never `clean`), a timeout in which the stub's grandchild process is proved gone afterwards, unrecognized output, a `package.json` without a lockfile, an unsupported manifest, a root with no manifest, a mixed root in which a finding wins over a precondition, the check order of R10, the usage error, `--json` and `--help`; for the engine, the drift test of R6, the options of R8 on both profiles and on the copy without a default, and a test that the legacy argument forms produce the bytes of the existing goldens. Tests of the new scripts SHALL run from a copy of the built skill directory outside the repository, under every package layout, as the `github-actions` tests do, so that a script that imports a repository file fails. Test files SHALL be named `scripts/tests/skill-scripts-security-*.test.ts` and `scripts/tests/skill-scripts-secrets-engine-*.test.ts`. The path filter of the job only triggers it: the `skill-scripts-ts` command in `taskfiles/ci/modules.yml` enumerates test files, so the implementation SHALL append the two families (as quoted globs, the form the `gitlab-ci` family already uses) to that command, as #1939 and #1940 did for theirs; a test file absent from the command never runs in CI.
14. **R14 (the sibling skills).** `github-actions` and `gitlab-ci` SHALL change in exactly two ways: the script of R6 replaces their `check-secrets-exposure.ts`, and each `SKILL.md` bumps `metadata.provenance.version` (a minor bump: an added option). No other line of either skill is edited. In particular both `SKILL.md` files, `references/` and `ci-configurator` keep citing `node scripts/check-secrets-exposure.ts <path>` with its one-argument form and its legacy exit codes, so `validate-pipeline.ts` of `github-actions` runs the engine unchanged, and the callers checks pass unchanged. Their `evals/` stay byte-identical. Sequencing with the CI agents work (spec 0302, issue #1942), which also adds references to `github-actions` and bumps its version: whichever of the two lands second SHALL rebase, renumber its version bump and spend the one measurement of R5 for the combined content, the first to land spending none if its change is not measured under its own spec; the measurement compares with the `evals/results.json` at the merge-base with `main` at that moment.
15. **R15 (security skill body).** `SKILL.md` SHALL be rewritten so that: it drops what the model already knows (the list of surfaces to review, the generic examples of credible threats per surface, the definition of a trust boundary) and keeps what it does not derive: the rule that a finding needs a traced path from a boundary to a sink and is otherwise not reported, the meaning of each severity with `BLOCKER` reserved for what must be fixed before merge, the secret-handling rules with the reason of each (a secret is never echoed in the report or the transcript, rotation guidance is part of the finding), the dependency review judgement (changelog between the versions, transitive and licence drift on a minor bump, a migration note on a major bump, reachability judged by the reviewer because the audit script does not assess it), the output format, the statement `No findings.` with what was examined when nothing credible exists, and the hand-offs (fixes to `developer`, pipeline hardening to `github-actions` or `gitlab-ci`, design questions to `architect`); it states when to run each script with its exit codes (`security-finding.ts` on the report before it is handed over, `dep-audit.ts` on a dependency change, `check-secrets-exposure.ts --platform <github|gitlab>` on CI definitions), that `dep-audit.ts` exit `3`, an `unsupported-ecosystem` warning and a `nothing-to-audit` warning all mean the dependencies were NOT audited and that this goes into the report, that when the review input is a diff the finding cites the post-image path and a new-file line (R9), that a clean review is the line `No findings.` followed by an `Examined:` line naming what was read, and that the engine keeps the legacy exit codes and has no `--json`; each retained rule states its reason; the body carries no spec, requirement or issue citation and no more than five capitalised `MUST`, `NEVER`, `CRITICAL`, `ALWAYS` or `IMPORTANT` outside code; the friction paragraph is replaced by a pointer to `references/shared-friction-reporting.md` and no text cites `config/TOOLS.md`; the frontmatter keeps `Bash` among its allowed tools and gains a `compatibility` that names Node.js 24 and says that `npm` and `pip-audit` are optional; and the body stays under 500 lines, with an aim of 150. A behaviour of the current skill dropped on purpose SHALL be listed on the logbook with its reason.
16. **R16 (description).** The `description` SHALL be third person, state what the skill does, carry a `Use when` clause with trigger terms (threat model, attack surface, trust boundary, authentication, authorization, session, secrets, credential leak, cryptography, deserialization, input validation, SSRF, dependency audit, CVE, dependency upgrade) and a `Not for` clause naming GitHub Actions workflows and GitLab pipelines (`github-actions`, `gitlab-ci`), applying a fix (`developer`), pull request verdicts (`pr-reviewer`), pull request descriptions (`pr-logbook`) and design alternatives (`architect`), within 1,024 characters.
17. **R17 (agent).** `artifacts/core/agents/security/AGENT.md` SHALL be rewritten so that: its `description` states when to delegate, with the trigger terms of R16, says that it returns findings and edits no file unless explicitly asked, and names what to send elsewhere (applying fixes to `developer`, pipeline authoring to `ci-configurator`), within 1,024 characters on the source and on every compiled output; the body states the role, the boundary (findings, not patches; the agent that finds the issue is not the one that closes it), the instruction to load the `security` skill with the `Skill` tool at the start of the session and follow it, the calls to the three scripts as `<security-skill-dir>/scripts/<name>.ts` with a skill-relative citation (so that `node scripts/check-agent-script-citations.ts` passes), the rule that when the skill or a script cannot be found it says so in its reply, continues with the manual protocol and never claims a check was run, and the hand-off; it carries no copy of the skill's lifecycle, severity scale, output format or activation list, no path under `artifacts/`, no spec or issue citation, and ends with one line pointing at the `harness-report` skill and not citing `config/TOOLS.md`. The paragraph that explained the withheld memory tools SHALL be removed with the allowlist.
18. **R18 (tools allowlist decision).** The agent SHALL declare no `metadata.tools`: the current allowlist `[read, search, web]` is removed. The agent runs the three scripts, which needs `execute`, and the rule of `docs/authoring.md` admits an allowlist only for an agent whose classes exclude `execute` and `edit`; an allowlist also withholds the `Skill` tool, which the agent needs to load its skill, and the current body reaches the skill by a repository path that does not exist in an adopter's installation. The read-only intent SHALL be kept as a plain statement in the description and the body. The deviation from the issue's wording (`read-only tools`) SHALL be recorded in the pull request description, on the logbook and as a comment on the wave checklist of parent issue #1854 (as spec 0302 R9 does for the CI agents), not in the runtime prompt, together with the rejected alternatives; the agent loses the enforcement of its read-only intent while it reads untrusted changes with a shell and edit tools available, and that is the accepted cost. The paragraph of `docs/authoring.md` (the *Declaring a tool allowlist* section, which names `security` as an agent that carries the allowlist) SHALL be updated in the same change so that it no longer names `security`.
19. **R19 (packaging).** The skill and agent sources SHALL bump `metadata.provenance.version` (a minor bump each) in the same change, the built components SHALL be regenerated in the same change, and every built `security` skill directory SHALL contain `scripts/` with the three scripts, `references/shared-friction-reporting.md` and no `evals/`. These SHALL pass: `task check-skill-quality -- security` (the skill ships evals, so it is protected and SHALL report no finding at all), `task check-skill-quality -- github-actions` and `task check-skill-quality -- gitlab-ci` with no new finding, `task check-description-length`, `task check-agent-script-citations`, `task check-agent-profiles`, `task check-metadata-keys`, `task check-skill-versions` and `task check-components`.
20. **R20 (integration points).** This change touches no CLI integration point (no deploy target, hook wiring, CLI root or settings, or CLI-specific `taskfiles/` entry; the appended test files of R13 go into the generic `skill-scripts-ts` command, which is not CLI-specific), so no `docs/cli-matrix/rows/` source and no `docs/cli-matrix.md` change is required; the scripts ship through the existing skill-resource propagation. If the implementation does touch one, the matrix row SHALL be updated in the same diff.

## Scenarios

### Happy path: a compliant report

- **Given** a report of two findings with bracketed severities from the five-word scale, the four fields each, and `Where:` values that name existing files and lines under `--root`,
- **When** `security-finding.ts` runs on it,
- **Then** it reports no finding, `data` counts two findings, and it exits 0.

### Failure path: a location that does not resolve

- **Given** a finding whose `Where:` is `src/handler.js:900` while the file has 40 lines, and another that names a file that does not exist,
- **When** `security-finding.ts` runs,
- **Then** it reports `where-line-out-of-range` and `where-file-missing`, each with the finding number and the fix, and exits 1.

### Failure path: the unmodified template

- **Given** the output template of the skill with its angle-bracket placeholders left in place,
- **When** `security-finding.ts` runs on it,
- **Then** it reports `placeholder` and `where-format` and exits 1.

### Edge: a clean review and an empty report

- **Given** one report holding the line `No findings.` and one empty file,
- **When** `security-finding.ts` runs on each,
- **Then** the first exits 0 with a count of zero and the second exits 1 with `no-findings-block`.

### Happy path: a clean audit

- **Given** a root with a `package-lock.json` and an `npm` stub on `PATH` that replays the clean capture,
- **When** `dep-audit.ts` runs,
- **Then** it exits 0 and `data` lists `npm` as audited and `clean`.

### Failure path: a vulnerable dependency

- **Given** a stub that replays the capture with one advisory at `high` and one at `low`,
- **When** `dep-audit.ts` runs with the default `--fail-on`,
- **Then** it exits 1 with one error finding and one warning finding, each naming the package, the severity and the fixed version, and stating that reachability was not assessed.

### Failure path: offline, missing tool and timeout never pass

- **Given** a stub that replays the offline capture, a `PATH` with no `npm`, or a stub that hangs past `--timeout 1` and has started a child process,
- **When** `dep-audit.ts` runs,
- **Then** it exits 3 with a `precondition` finding naming the cause and stating that the dependencies were NOT audited, `ok` is false, and after a timeout neither the stub nor its child remains.

### Failure path: a Windows host

- **Given** a Windows host,
- **When** `dep-audit.ts` runs with valid arguments,
- **Then** it exits 3 with a `precondition` finding of cause `unsupported-platform` and looks up no tool.

### Edge: nothing to audit, unsupported and mixed roots

- **Given** a root with no manifest, a root with only `go.mod`, and a root where `npm` reports a vulnerability while `pip-audit` is missing,
- **When** `dep-audit.ts` runs on each,
- **Then** the first exits 0 with `nothing-to-audit`, the second exits 3 with an `unsupported-ecosystem` warning and nothing audited, and the third exits 1 while `data` still shows `pip` as `not-audited`.

### Happy path: the legacy forms of the engine are unchanged

- **Given** the goldens captured from the two replaced scripts and the copies of the engine in `github-actions` and `gitlab-ci`,
- **When** the existing suites run on the new copies with the one-argument forms and the help forms they pin,
- **Then** stdout, stderr, exit code and files written are byte-identical, `--help` is identical to the legacy text, and no existing test or golden was edited.

### Failure path: the security copy has no default platform

- **Given** the engine in the `security` skill and a target file,
- **When** it runs without `--platform`, with `--platform bitbucket`, and with `--platform gitlab`,
- **Then** the first two exit 2 naming the option and the values `github` and `gitlab`, and the third scans with the `gitlab` profile and exits 0 or 1 as the legacy script would.

### Edge: help wins over an invalid platform

- **Given** the engine in the `security` skill,
- **When** it runs with `--platform bitbucket --help`,
- **Then** it prints the usage and exits 0, whereas `--platform bitbucket` alone exits 2.

### Failure path: a copy drifts

- **Given** a copy of the engine in a sibling skill with one changed pattern outside the marked line,
- **When** the drift test runs,
- **Then** it fails naming the file and the first differing line, and it passes again when only the default-platform line differs.

### Failure path: the agent without its skill

- **Given** an installation in which the `security` skill or its scripts are absent,
- **When** the `security` agent reviews a change,
- **Then** it says which file it could not find, follows the manual protocol, and does not state that a check was run.

### Failure path: a measurement regresses or the budget is spent

- **Given** a final measurement below the baseline by more than the tolerance or below 0.80, or four paid measurements spent for one skill,
- **When** the contributor revises the description, then the body, within the cap,
- **Then** the cases stay unchanged and, if the criteria still fail, no further run is made, no check is bypassed and the figures go to the user for decision.

## Out of scope

- Any change to `github-actions` or `gitlab-ci` other than the engine copy and the version bump of R14, the CI agents (`ci-configurator`, `ci-debugger`, `ci-parity`, issue #1942) and the eval runner and its settings.
- A shared-script mechanism in the build, and a `--json` option or exit `3` for the secrets engine (a change that needs a bounded delta of spec 0258).
- Dependency audits for ecosystems other than `npm` and `pip`, automatic fixing of a dependency (`npm audit fix`), reachability analysis, and a check that a report's evidence occurs at its cited line.
- Secret-shape detection in a findings report, and secret scanning of a repository outside CI definitions.
- Editing the spec 0258 oracle, its goldens or its case tables.
- Wiring the new scripts into the repository's own pipelines.

## Open questions

- Decided (AUTO): where the engine lives. Three routes were weighed. (a) The `security` skill owns it and the siblings call `<security-skill-dir>/scripts/...`: rejected, because a skill must install alone, `validate-pipeline.ts` of `github-actions` runs the engine from its own directory, and the `ci-configurator` citations and the callers suites name the script in each sibling. (b) A new build step that copies a shared script into each skill, as the build does for shared references: rejected, because the shared mechanism is limited to `shared-*.md` references and a script copied under another name would break the callers and `--help` checks, while the pinned oracle reads the scripts at their source path; the build, the citation grammar, the linter and the drift check would all change for one file. (c) Committed copies with one marked line and a drift test: chosen, because it is the deliberate duplication of rule 7 of the script contract with a guard, it leaves every pinned path, citation and golden alone, and the cost is one test.
- Decided (AUTO): the default platform is a marked line in each copy, not a guess from the skill directory name, because the `validate-pipeline` tests run the engine from copies named `skill-<n>`, and a guess from the target is not reproducible byte for byte.
- Decided (AUTO): the agent keeps no allowlist (R18). Three alternatives were rejected: split the agent into a read-only reviewer and a script runner; keep the allowlist and leave the scripts to the delegating session; and keep the allowlist with a thin runner agent that executes the three scripts. The last two trade one hand-off for an enforced boundary, but the reviewer then cannot check its own report or audit a dependency while it reviews, which is the failure mode of the current agent, and the allowlist would still withhold the `Skill` tool that loads its skill. Standing with the choice means the read-only boundary is a statement, not an enforcement.
- Decided (AUTO): `dep-audit.ts` ships `npm` and `pip` only, and only with real captures (R11); other ecosystems are named and reported as not audited, because a recognition rule written from documentation is the failure that the `lint-gitlab-ci.ts` captures were introduced to prevent.
- Decided (AUTO): sequencing with #1942 is normative in R5 and R14. The implementation starts now that `github-actions` and `gitlab-ci` are modernized on `main`.
