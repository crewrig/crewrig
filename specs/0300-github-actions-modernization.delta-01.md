# Modernize the github-actions skill and the ci-configurator agent to the authoring standard

*Delta 01 of `specs/0300-github-actions-modernization.md`. Source: issue #1939, plan review v1 (findings v1-F1 and v1-F2, class `spec`). The original R10 changed exit codes and messages of the five existing scripts of the skill, which spec 0258 pins through its differential and golden oracle (R4, the closed list of deviations of R31 and its delta-01). Recording those changes needs a delta of 0258 and would collide with sibling #1940, whose spec 0301 R8 moves `check-pinned-images` in the same oracle. Decision of the orchestrator, not reopened here: the existing scripts only GAIN `--help` and `--json`, every exit code and message stays byte-identical, and the new scripts alone follow the full 0/1/2/3 contract. Revised after the seat verdict of pull request #1946 (s3-F1 to s3-F4): three 0258 goldens that pin `--help` as legacy behaviour are named as the only exception, the `--json` error findings carry distinct rule ids, the fan-out of `validate-pipeline.ts` over the legacy one-argument scripts is defined, and the new scenario moves to ADDED. Requirements modified: R6 (scope sentence and check order), R10, R11 (`validate-pipeline.ts`), R21 and the scenario "empty directory, unreadable input, missing tool"; the Out of scope list is extended. Every other requirement is unchanged. This delta opens no question.*

## ADDED

No requirement is added. The two orderings and the exit-code mapping that v1-F2 asked to settle are written into the amended R6, R10 and R11 below. One scenario is added.

### Failure path — existing scripts stay identical except three named `--help` goldens

- **Given** the five existing scripts of the skill and the 0258 differential and golden suites, in which exactly three cases pin `--help` as legacy behaviour (`simulate-job/help-flag`, `simulate-workflow/help-flag`, `check-pinned-actions/help-flag`),
- **When** the suites run on the rewritten skill after the PLAN has regenerated exactly those three goldens,
- **Then** every other case passes with its golden, deviation entry and fold unedited, `--help` exits 0 with the usage text on all five scripts, and `--json` returns the `{ok, data, findings}` object on the four that gain it, with the golden captures of that flag passing.

10. **R10 (existing scripts: audit and scope), original:** "The five existing scripts do not follow the contract today: none accepts `--help` (each treats it as a path and exits 1 or 0) and none offers `--json`. This change SHALL bring `lint-workflow.ts`, `check-pinned-actions.ts`, `simulate-job.ts` and `simulate-workflow.ts` onto the contract (`--help`, `--json`, exit codes 0/1/2/3, ...) ... except for the explicit exit-code and message changes below ((a) missing input exit 1 to 3, (b) empty directory exit 0 to 2, (c) tool status passed through to exit 1, signals 128+n to 1, (d) internal error 1 to 3, (e) `--help` as exit 0) ... A missing external tool ... SHALL stay a skipped check with exit 0 ... `check-secrets-exposure.ts` ... the single permitted edit is the minimal handling of `--help` ..."

**Amended (R10):** The five existing scripts, `lint-workflow.ts`, `check-pinned-actions.ts`, `simulate-job.ts`, `simulate-workflow.ts` and `check-secrets-exposure.ts`, are pinned by the differential and golden suites of spec 0258 (R4 and the closed deviation list of R31 with its delta-01). This change SHALL therefore make only additive changes to them, and SHALL NOT change any of their observable behaviour that those suites exercise:

- **(a) Additions.** `lint-workflow.ts`, `check-pinned-actions.ts`, `simulate-job.ts` and `simulate-workflow.ts` SHALL gain `--help` (usage on standard output, exit 0) and `--json` (a single object `{ok, data, findings}` on standard output in place of the human-readable text, with the same exit code the run would have had without `--json`). `check-secrets-exposure.ts` SHALL gain `--help` only, because `task check-skill-quality` runs every script of a protected skill with `--help` and reports an error otherwise; its `--json`, its detection and its replacement by the shared engine belong to sibling #1941. `--help` is today pinned as legacy behaviour by exactly three goldens of the 0258 oracle, found by searching the cases under `scripts/tests/lib/skill-scripts-cases-github*.ts` and the golden directories for `--help`: `simulate-job/help-flag` (status 2, usage on standard error), `simulate-workflow/help-flag` (status 1, `[FAIL] workflow file not found: --help`) and `check-pinned-actions/help-flag` (status 1, `[FAIL] not a file or directory: --help`). `lint-workflow.ts` and `check-secrets-exposure.ts` have no such golden. These three goldens are the single named exception of this change: they SHALL be re-recorded as the new behaviour, `--help` exits 0 with the usage text on standard output, and nothing else in the 0258 goldens, deviation entries or folds changes. A bare `--json` argument was never a valid path either and is pinned by no case.
- **(b) Unchanged, byte for byte.** Without `--json`, standard output, standard error and the exit code of every existing script SHALL stay identical to today for every input except the `--help` argument of the three scripts named in (a), and that includes: an unreadable or missing input path (exit 1, and for `simulate-job.ts` the `[FAIL] workflow file not found` line, for `simulate-workflow.ts` also `[FAIL] event payload file not found`), a directory with no workflow file (exit 0, the `[OK]` line of `check-pinned-actions.ts` and the `[SKIP] no workflow files found under: <target>` line of `lint-workflow.ts`), the non-zero status of `actionlint` or `act` passed through verbatim by `simulate-job.ts` and `simulate-workflow.ts` (a tool killed by a signal keeps its present handling), the end of `simulate-workflow.ts` after SIGINT or SIGTERM (status 128 plus the signal number, temporary payload file removed), an unexpected internal error (exit 1), usage errors (exit 2) and findings (exit 1). The existing exit-0-with-`[SKIP]` behaviour for a missing tool (`actionlint`, `act`, the `docker` CLI or daemon) stays, and the existing order stays: the tool check runs before the target check, so a missing tool with a missing target or an empty directory is still exit 0 with the `[SKIP]` line.
- **(c) Under `--json`.** A skipped external tool SHALL be reported as a warning finding `tool-missing` and `ok: true`, with the exit code the legacy run has (0). A legacy error path under `--json` SHALL report an error finding and keep the legacy exit code, so no mapping to 2 or 3 exists for these scripts. Each path carries its own reserved rule id, distinct from every lint rule of `actionlint` and every pin rule of `check-pinned-actions.ts`: `usage` (wrong arguments, legacy exit 2), `target-unreadable` (missing path, exit 1), `tool-failed` (a spawn failure, a tool killed by a signal, or a non-zero status of `act` or of a failed `actionlint` run that is not a lint result, and the SIGINT or SIGTERM end of `simulate-workflow.ts`, with its present exit code) and `internal-error` (an unexpected error, exit 1). These four ids are reserved: no lint or pin finding uses them. The `--json` output is new surface: it is pinned by golden captures (below), not by the 0258 suites.
- **(d) Proof.** Apart from the three goldens named in (a), the existing 0258 differential and golden suites SHALL pass unchanged: the contributor SHALL NOT edit any other 0258 golden file, deviation entry or fold, and SHALL NOT mint a new deviation letter for any other case. The PLAN SHALL regenerate exactly those three goldens (and no other) as the new `--help` behaviour and choose how the oracle records them, within those three cases. The new flags SHALL be pinned by golden captures of `--help` and `--json` stored with the tests of this skill, outside the 0258 oracle.
- **(e) Where the full contract lives.** The exit codes 0/1/2/3 of R6 apply to the five new scripts only. A migration of the legacy scripts onto them is out of scope here and needs a delta of 0258.

The rest of R10 (its audit sentence aside) is replaced by the five points above.

11. **R11 (agent-facing scripts), `validate-pipeline.ts` bullet, original:** "`validate-pipeline.ts <workflow-file-or-directory>...` SHALL run, from the same directory, `lint-workflow.ts`, `check-pinned-actions.ts`, `check-permissions.ts`, `check-pull-request-target.ts`, `check-expression-injection.ts` and `check-secrets-exposure.ts` on its inputs, and report each check as `ran` and passed, `ran` with findings, or `skipped` with the reason (the check script absent or its external tool missing). It SHALL exit 1 when any check that ran reported an error finding, and 0 otherwise. ..."

**Amended (R11, `validate-pipeline.ts`):** `validate-pipeline.ts <workflow-file-or-directory>` SHALL take exactly one input, because every legacy script takes exactly one argument and none reads standard input. It follows this order:

1. A usage error is exit 2, and that includes zero or several inputs and the input `-`: the pipeline SHALL reject `-` with a usage message naming the reason (the legacy scripts cannot read standard input), rather than materialise a temporary file. The permitted route for a piped workflow is to write it to a file first. The `-` input of R6 therefore applies to the three new check scripts run on their own, not to the pipeline.
2. Target validity comes next. An unreadable or missing input is exit 3. A directory input is resolved by one rule, the one the legacy scripts already apply: when `<dir>/.github/workflows` is a directory the walk starts there, else at `<dir>` itself; the walk is recursive and keeps the files whose names end in `.yml` or `.yaml`, sorted by bytes. A file input is its own single-file set. An empty set is exit 2 with `[FAIL] no workflow files found under: <target>`. No check has run and no tool has been looked for when either occurs.
3. Only then does it run the six checks, `lint-workflow.ts`, `check-pinned-actions.ts`, `check-permissions.ts`, `check-pull-request-target.ts`, `check-expression-injection.ts` and `check-secrets-exposure.ts`, from the same directory. It SHALL run each script once per file of the resolved set, passing that one file as the sole argument, so that the legacy and the new scripts see the same file set whatever the directory layout, and it merges the per-file results into one report per check. It SHALL report each check as `ran` and passed, `ran` with findings, `skipped` with the reason (the check script absent, or its external tool missing) or `failed`, and SHALL never mark a check `ran` that was skipped.

How it reads each check:

- The three new checks: exit 0 is `ran` and passed, exit 1 is `ran` with findings, and any other status, a signal or a spawn failure is `failed`.
- `lint-workflow.ts` and `check-pinned-actions.ts`: it calls them with `--json` and reads the object and the legacy exit code. A `tool-missing` warning finding with exit 0 is `skipped` (tool missing). Any finding whose rule id is one of the four reserved ids of R10(c), `usage`, `target-unreadable`, `tool-failed` or `internal-error`, makes the check `failed`, whatever the exit code. Otherwise exit 0 is `ran` and passed and exit 1 with error findings is `ran` with findings. Because the reserved ids never appear on a lint or pin finding, a failure to run is never reported as a finding on the workflow, and the `failed` branch is reachable by a test that makes `actionlint` fail to spawn or removes the target between the validity check and the run.
- `check-secrets-exposure.ts`: it reads the exit code only and never its output, so it works whether or not sibling #1941 has landed, in either merge order. Exit 0 is `ran` and passed; exit 1 is `ran` with findings, with the script's standard output and standard error relayed verbatim in the report, since a finding and an internal error share that code; any other status, a signal or a spawn failure is `failed`.

The pipeline SHALL exit 1 when any check that ran reported an error finding, 0 when every check ran and passed or was skipped, and 3 when any check `failed`, the failed check being named. It writes nothing and makes no network call. The `resolve-engine.ts` bullet of R11 is unchanged.

Order for the new scripts in general (answers v1-F2): for `check-permissions.ts`, `check-pull-request-target.ts`, `check-expression-injection.ts`, `resolve-engine.ts` and `validate-pipeline.ts`, usage is checked first (exit 2), then target validity (empty directory exit 2, unreadable path exit 3), and only then the availability of an external tool. A missing tool is never reported ahead of an invalid target for these scripts. The three checks and `resolve-engine.ts` need no external tool.

### Failure path — empty directory, unreadable input, missing tool

- **Given** a directory with no workflow file, an unreadable path, or a machine without `actionlint`,
- **When** a new check (`check-permissions.ts`, `check-pull-request-target.ts`, `check-expression-injection.ts`) or `validate-pipeline.ts` runs, or an existing script (`lint-workflow.ts`, `check-pinned-actions.ts`) runs on the same input,
