# Agent frontmatter: the model on Claude Code and a least-privilege tool allowlist

*Delta 01 of `specs/0291-agent-model-tools-allowlist.md`. Source: issue #1991, follow-up F4 of ADR-0025 (epic #1930). ADR-0025 (*Path to the targets*) measured that a subagent in a vanilla session reaches 16,769 tokens only with a `tools` allowlist that includes `Skill`, and states that CrewRig cannot emit such an allowlist for an editing agent: R17 forbids `execute` and `edit` in an allowlist, and the vocabulary has no class for `Skill` or `SendMessage`, which R16 says an allowlist withholds. This delta adds the two classes and relaxes R17. Version 1.1.0, a MINOR bump: the vocabulary grows and R17 stops rejecting; no existing declaration changes meaning. Requirements R1 to R7, R9, R12 to R14, R18 to R24 and R26 to R27 are unchanged (R18 and R19 describe the original change and stay true of it; R22 and R25 are extended by R32 and R33 below). The table of R11 is extended by R28 rather than rewritten. Tier `small`, fixed by the coordinator from the sizing of issue #1991 and the follow-up table of ADR-0025: the change is a mechanical extension of an existing closed vocabulary through the existing emitters, with no new abstraction, no new script, no new CI surface and no agent source edited; its footprint of about ten files is documentation and goldens. This delta opens no question.*

    Grounding, read on 2026-11-14 (no CLI version stated): Claude Code, the background-subagent tool list of <https://code.claude.com/docs/en/sub-agents> already cited by R16, which names `SendMessage` and `Skill` (that an allowlist also withholds them remains the INFERENCE R16 labels, not a statement of the page); Gemini CLI, the table of <https://geminicli.com/docs/reference/tools/>, which lists `activate_skill` ("loads specialized procedural expertise from the `.gemini/skills` directory") and no tool that sends a message to a parent agent (`complete_task` "returns the result to the parent agent" and ends the mission, so it is not a message channel and SHALL NOT be mapped); Copilot CLI, <https://docs.github.com/en/copilot/reference/custom-agents-configuration>, whose primary aliases are `execute`, `read`, `edit`, `search`, `agent`, `web` and `todo` and which names no skill tool and no tool for messaging a caller. Evidence of search for the three empty cells (Copilot `skill`, Copilot `message`, Gemini `message`): beyond the pages above, <https://docs.github.com/en/copilot/concepts/agents/about-agent-skills> (read 2026-11-14) states no way to name a skill in a custom agent's `tools` list and no hook path, and lists the user-level (`~/.copilot/skills`, `~/.agents/skills`) and project-level (`.github/skills`, `.claude/skills`, `.agents/skills`) locations, which are skill discovery paths and not an allowlist name; <https://geminicli.com/docs/core/subagents/> (read 2026-11-14) states that a subagent \"reports back to the main agent with its findings\" on completion, describes user-level (`~/.gemini/agents/*.md`) and extension-bundled agents only as definitions, mentions hooks without any subagent channel, and never names `activate_skill` in the `tools` key (the name is grounded on the identifier table, like the other Gemini names). No user-level, hook-level or alternative-path mechanism supplying a name or a channel was found. That is evidence about the documented surface only, so the cells stay `[GAP-confirmation]` (R29) until a probe on a named ticket or a documentation change shows a name, which SHALL NOT be guessed.
29. **R29 (non-silent drop on Copilot and Gemini).** The Copilot emitter SHALL omit a class that has no Copilot name (`skill`, `message`), the Gemini emitter SHALL omit `message` (and `agent`, R13), and each SHALL emit one `tools-drop` line per omitting agent (R7 grammar, declared classes the omitted ones, reason `no-equivalent-on-cli`) on standard error and in the `--diagnostics` file. The failure of R13 generalizes: when omitting classes leaves a Copilot or Gemini agent no tool, the build SHALL fail as R10 and no empty list is written (an agent declaring only `[skill]` or `[message]` fails for Copilot). R13 stays otherwise unchanged; the error of the failure path is generalized, because `noGeminiTool` in `scripts/lib/build-components/agent-tools.ts`, thrown from `scripts/lib/build-components/emit-agents.ts`, words it for Gemini CLI today ("has no Gemini CLI name for ... subagents cannot call other subagents"), and its message SHALL name the CLI and the reason (no name on that CLI) for Copilot as for Gemini. The Antigravity emitter is unchanged (R14: no `tools` key, one `tools-drop` line with the declared classes, `unsupported-on-cli`). On the shared `.claude/agents/` surface, a Copilot reader sees `Skill` and `SendMessage` as unknown names, which it ignores as it ignores `Agent` (R16), failing toward fewer tools; the docs SHALL say so. The gaps SHALL be recorded as `[GAP-confirmation]` in `docs/cli-matrix/parity-gaps.md`, with the condition that lifts each (a documented name or a probe on a named ticket).

31. **R31 (no agent source in this change).** No core or library agent source SHALL declare `skill` or `message`, and none SHALL be edited by this change, so no `metadata.provenance.version` is bumped, `scripts/check-skill-versions.ts` has nothing to flag, and no compiled agent output changes (R12 holds for every shipped agent). ### Scenarios

**Scenario:** the new classes in vocabulary order

```text
Given an agent source declaring metadata.tools: [message, skill, edit]
When  the component build runs for all four CLIs
Then  the Claude file carries "tools: Edit, Write, Skill, SendMessage"
And   the Gemini file carries "tools: [write_file, replace, activate_skill]" and the stream carries one tools-drop line for message with reason no-equivalent-on-cli
And   the Copilot file carries "tools: [edit]" and the stream carries one tools-drop line for skill, message with reason no-equivalent-on-cli
And   the Antigravity file carries no tools key and the stream carries one tools-drop line with reason unsupported-on-cli
```

**Scenario:** a declaration that leaves no tool on a CLI

```text
Given an agent source declaring metadata.tools: [skill, message]
When  the component build runs for the copilot target
Then  it exits non-zero, naming the file, the key and the declared classes, rather than writing an empty tools list
And   for the gemini target it writes "tools: [activate_skill]" and one tools-drop line for message
```

**Scenario:** the refusal names eight classes

```text
Given an agent source declaring metadata.tools: [shell]
When  the component build runs
Then  it fails naming the file, the key, the value shell and the admitted classes read, search, edit, execute, web, agent, skill, message
```

**Scenario:** no shipped agent changes

```text
Given the sources of the shipped agents unchanged
When  node scripts/build-components.ts --check runs
Then  it passes and no metadata.provenance.version differs from main
```

- **R17 (the rule).** Original: "An allowlist SHALL be declared only for an agent whose classes exclude `execute` and `edit`. Replacement: "An allowlist MAY be declared for any agent, whatever its classes. The sentence "an allowlist withholds every tool it does not name, so an editing agent's allowlist names skill" SHALL appear in `artifacts/FORMAT.md` and `docs/authoring.md`, with its rationale: an allowlist withholds every tool it does not name, `Skill` and `SendMessage` included (R16), so an agent that has `edit` or `execute` and omits `skill` loses the skill listing and the `Skill` tool that its body tells the model to use, and an agent that reports to its caller through `SendMessage` and omits `message` loses that channel; the `skill` class SHALL therefore be named by every allowlist that contains `edit` or `execute`, and the `message` class SHALL be named by every allowlist of an agent whose body talks to its caller through `SendMessage` (ADR-0025, *Path to the targets*: a subagent in a vanilla session reaches 16,769 tokens only with an allowlist that includes `Skill`; row 4c of the CLI matrix). `scripts/check-component-metadata-keys.ts`, which admits `metadata.tools` (R9) and whose enforcement point is `scripts/lib/governance/metadata-keys.ts` (the constant `BANNED_CLASSES` and the K2 message that cites R17 and says \"an allowlist is declared only for an agent whose classes exclude execute and edit\", both replaced), SHALL enforce the part it can decide: it SHALL reject, naming the file and the class `skill`, a `metadata.tools` that contains `edit` or `execute` and does not contain `skill` on an `AGENT.md` under `artifacts/core/` or `artifacts/library/`, and its K2 message SHALL cite R17 as amended, and SHALL accept every other combination of the eight classes, `[read, execute, skill]` and `[read, search, web]` included; it SHALL NOT judge `message`, which depends on the body and is left to review. The adopter tiers `artifacts/community/` and `artifacts/org/` are outside the check, as they are outside R9. The build and emitters (R10 to R14) are not bound by the rule and accept the whole vocabulary. The rationale of the original, that with `execute` the restriction protects nothing because a shell can write files and mutate remote state, stays true and is why an allowlist is a context-size tool for such an agent (ADR-0025) and not a protection."
