# ADR 0023 — Skill eval executor, judge routing and attestation

<!-- crewrig-doc: section=architecture-adr nav_order=230 published=true title="ADR 0023 — Skill eval executor, judge routing and attestation" -->

**Status:** Accepted (issue #1849); amended by deltas 02 and 03 (issue #1874) and delta 04 (issue #1884). Decided by [spec 0290](../../specs/0290-skill-eval-runner.md), its [delta 01](../../specs/0290-skill-eval-runner.delta-01.md), its [delta 02](../../specs/0290-skill-eval-runner.delta-02.md), its [delta 03](../../specs/0290-skill-eval-runner.delta-03.md) and its [delta 04](../../specs/0290-skill-eval-runner.delta-04.md); delta 03 moves the executor from a throwaway home to isolation by flags on the logged-in session, delta 04 reduces the runner to one run and one judge call per eval. Operating guide: [`docs/skill-evals.md`](../skill-evals.md).

## Context

A maintainer who changes a skill should learn, before the change merges, whether an agent with the skill passes the skill's own evaluation cases and loads the skill when it should. The repository needs a runner that runs each case of `evals/evals.json` once, non-interactively, compares the answer with what was expected, and gives a pull-request signal. Running evals costs money and is nondeterministic, so the runner does the least that answers the question: one run and one judge call per eval, no run without the skill, no replay on the base revision.

## Decisions

1. **Executor: headless Claude Code, isolated by flags.** `claude -p --output-format stream-json --setting-sources project --strict-mcp-config --no-session-persistence`, with the contributor's real `HOME` and `CLAUDE_CONFIG_DIR` (never `--bare`), the skill installed at project scope as `<workspace>/.claude/skills/<name>/` (`SKILL.md`, `scripts/`, `references/`, `assets/`, never `evals/`), a temporary workspace outside any repository and outside `HOME` (a `TMPDIR` inside `HOME` or a git work tree exits 3), an allowlisted environment (including `USER` and the CA and proxy variables), one process group per run killed at the wall-clock limit. A throwaway `HOME` or `CLAUDE_CONFIG_DIR` was dropped: the delta-03 smoke showed `claude` answers `Not logged in` under either. It exercises a skill exactly as it runs when installed, scripts included.
2. **Model pin: a Sonnet-class model (`claude-sonnet-5-5`) at effort `medium`.** It is the current Sonnet, the cost and capability tier the shipped agents run on, and it keeps a per-run budget of 1 US dollar meaningful; `claude` 2.1.322 accepted the name in the delta-03 smoke. `EXECUTOR_MODEL` and `JUDGE_MODEL` are single, documented settings; a run never silently uses another model. The effort is the `EFFORT` setting, default `medium`, passed as `--effort` to the executor, the probe runs and the judge call; the `anthropic` driver used under `--use-api-key` has no effort level. Whether `medium` lowers the cost of a run is for the pilot to measure. This supersedes `claude-sonnet-4-6`; recorded results files keep the model they were produced with.
3. **The eval measures a skill on Claude Code only.** Not on each of the four CLIs the skill ships to. No CLI-matrix row is added: the runner is a repository development tool and deploys nothing to a CLI target.
4. **Judge follows the credential and never sends the subscription credential to the Messages API.** The credential source is, in order: `ANTHROPIC_API_KEY` only under the explicit `--use-api-key`, then `CLAUDE_CODE_OAUTH_TOKEN`, then the contributor's logged-in Claude Code session (the default, probed by `claude auth status --json` before any model call; not logged in exits 3). With the token or the session the judge's calls are made by headless `claude -p` through an evidence-mode driver (`tests/e2e/lib/llm_judge_drivers/claude-cli.ts`, `complete()` only) under the same isolation flags; the existing `anthropic` driver is used only under `--use-api-key`. Without that option `ANTHROPIC_API_KEY` is removed from every `claude` child, because `claude` prefers it to the login. Whether a `setup-token` value may be used as a Bearer outside the `claude` binary is a terms-of-use question that is not decided here; the existing `claude-code` driver is not changed and an effective configuration that would send the token (or the session's OAuth credential) to the Messages API is refused (exit 3). The question is deliberately out of scope; the runner routes around it by judging through `claude -p`.
5. **Judging through the shared library, in a single call.** An evidence-mode entry point (`llmJudgeEvidence`) lives in `tests/e2e/lib/llm_judge.ts`. It makes one model call per eval, covering all of the eval's expectations, answered as one `<n> VERDICT=<PASS|FAIL> EVIDENCE=<JSON string>` line per expectation; the `max_calls` cap and the mock mode are inherited. The runner is its only caller, so there is no quorum parameter. `llmJudge` keeps its three-call quorum, and its output, exit codes and request bytes stay pinned by the existing differential goldens. Lines, not one JSON answer, so that a missing verdict is a per-expectation failure instead of a parse failure of the whole answer.
6. **Evals run on the contributor's machine; CI verifies a committed, content-hashed attestation.** A real run writes `evals/results.json` holding a SHA-256 content hash; the pipeline recomputes the hash and compares. The pipeline makes no model call and holds no secret.
7. **Caps.** Per skill: 20 executor runs (evals plus probes) and 20 judge calls; per invocation: 100 US dollars of worst-case executor cost; 4 runs in flight; per run: 25 turns, 300 seconds, 1 dollar. All provisional, to be recalibrated from the measured costs of the `pr-logbook` pilot (issue #1852). A migration pull request whose worst case exceeds the invocation cap is refused by default and must be split or the setting raised.

## Trust model

The attestation is self-declared: nothing proves a results file came from a run of the runner, so it is forgeable by design and any forged file is visible in code review. The check proves freshness, not truth. This is accepted because the alternatives below are worse for a required check.

## Alternatives rejected

- **CI runs the evals with a repository secret.** A pull-request-controlled script, and an agent with `Bash`, can read the secret; fork pull requests would silently skip the gate; cost and flakiness would enter a required check; the secret would have to exist on both engines.
- **Direct Messages API with our own tool loop.** It does not install a real skill and re-implements skill discovery.
- **Claude Agent SDK.** It adds a root production dependency for the same engine.
- **`--bare`.** It never reads the OAuth login or the keychain, so it cannot run on a logged-in session; it stays forbidden.
- **Project-scope `.claude/skills` (reconciled by delta 03).** Originally rejected because it loaded repository rules and made the arms asymmetric. It is now used: the workspace is a temporary directory outside any repository and outside `HOME`, so no repository rule or ancestor memory file is loaded, and both arms share the same flags and differ only by the presence of the installed skill.
- **Reusing the existing `claude-code` driver with the subscription token.** Terms and acceptance are unverified, and it would widen an e2e contract.
- **A paired run without the skill, a replay on the base revision and a three-call quorum (removed by delta 04).** They tripled the executor runs and multiplied the judge calls for a comparison the owner did not ask for. `skill_loaded` records whether the skill was used; regression compares the pass rate with the base's committed `results.json`.
- **Treat a limit hit as an error.** It lets a looping skill hide and is flaky on slow machines.

## Consequences

- The runner needs the `claude` binary; Windows is unsupported for the executor.
- The first live runs are a maintainer smoke: `total_cost_usd` in the result record, `--max-turns` (accepted by the executor in the delta-03 smoke; the runner counts turns itself, one per assistant `message.id`, and that count is the primary guard), `claude -p` as a judge on the logged-in session, and a run with four concurrent runs.
- The caps and the regression tolerance are provisional until the pilot has produced measured costs.

## Residual risk and prerequisites (delta 03, requirement 44)

Operating detail: [`docs/skill-evals.md`](../skill-evals.md#residual-risk-and-prerequisites).

- **Prerequisite.** Claude Code installed and logged in. `claude setup-token` (`CLAUDE_CODE_OAUTH_TOKEN`) and `ANTHROPIC_API_KEY` are optional overrides.
- **API key opt-in and credential exposure.** `ANTHROPIC_API_KEY` is used only with `--use-api-key`. In session mode the credential is no longer in the agent's environment, so the agent's `Bash` cannot read it from there. Where Claude Code keeps the login in a file under the real configuration directory instead of the keychain, that file is reachable by the agent's `Read` and `Bash`, and the residual is not reduced. On macOS the login is held in the keychain, which the agent's `Bash` may still reach through the `security` command, subject to the operating system's own prompt, so the keychain is not unreachable. With `CLAUDE_CODE_OAUTH_TOKEN`, or with `ANTHROPIC_API_KEY` under `--use-api-key`, the credential is in the child's environment and the previous residual stands unchanged.
- **Filesystem reach.** The agent runs as the contributor with the real `HOME`, so its `Bash`, `Read`, `Write` and `Edit` can reach and modify the contributor's configuration directory. The previous throwaway `HOME` never confined the filesystem (an absolute path always reached it); it only removed the default pointer. No tool-level deny rule is added: `Bash` would bypass it and the rule would be a false boundary.
- **Shared state files and concurrency.** `claude` may update its own state files in the configuration directory (for example a credential refresh), and runs in flight share it. Concurrency stays at its default of 4 in session mode, to be verified by the maintainer smoke run with four concurrent runs; `EXECUTOR_CONCURRENCY` is lowered if refreshes interfere.
- **Measured cost.** An isolated run on Sonnet 5.5 costs about 0.03 US dollars (0.022 for a one-word reply, 0.028 for a skill-triggered run of five turns, 0.025 without the skill). It is an input to the recalibration of issue #1852; no cost default changes.
- **Checked-out pull requests.** Running the evals on a pull request that is not the contributor's own executes its skill and scripts as the contributor, with the real `HOME`; the contributor reviews the skill's scripts first. Delta-01 requirement 38 covers the forgeability of results, not this.
- **Network variables.** The passed-through network variables are configuration, but a proxy URL may embed credentials that the agent's `Bash` can read; they are the contributor's own, at the same trust as the login.
